# Verification: offline (docs lens) — independent check, 2026-10-06

## Overall
Within the lens of published facts the report is mostly reliable. Release dates, stars, licences, archive dates, maintainer quotes, the KDBX specification points, CVE-2023-32784, the Maven data and the kotpass-to-KeePassXC round trip (reproduced here) all check out against primary sources. One date is wrong: Padloc v4.3.0 was published on 2023-03-06, not 2023-04-28. One distribution fact went stale three days ago: Keepass2Android's main app is no longer on Google Play, and only the Offline app at 1.14-r0 is listed. Before we rely on the report, it should fix those two, mark the KeePassDX clipboard issues and the KeePassJava2/kotpass problems as closed or fixed, replace '#505 open' with KeePassDX's documented 'will not offer' CSV stance, and add two design inputs it missed: bounding KDF parameters (KeePassDX #2640) and Android's Credential Exchange (CXF) import/export API.

## Not confirmed
- [refuted] (claim 2) Padloc's last release was v4.3.0 on 2023-04-28.
  - evidence: The release page shows 'github-actions released this 06 Mar' (datetime=2023-03-06T16:05:49Z). One api.github.com call for releases/tags/v4.3.0 returned published_at 2023-03-06T16:05:49Z and created_at 2023-03-05T14:37:54Z. The date 2023-04-28T07:07:11Z is only the Atom feed's <updated> value, which records a later edit of the release.
  - correction: v4.3.0 is still Padloc's last release, but it was published on 2023-03-06 (the tagged commit is from 2023-03-05). The last commit on main is from 2023-12-10. Dates taken from releases.atom <updated> can be edit dates; for the other releases I checked, they matched the publication date.
- [corrected] (claim 3) Keepass2Android is on Google Play.
  - evidence: Today play.google.com/store/apps/details?id=keepass2android.keepass2android returns 404 for gl=US, DE, GB and UZ, the same response as a non-existent package (Bitwarden's page returns 200). The developer's Play page lists only keepass2android_nonet, plugin.qr, AncientIconSet and the donate app. Issue #3320 (opened 2026-10-03) is titled 'No more Keepas2android online version on Google Play store?'. Commit 76d8502 (2026-10-05) is titled 'Remove donation menu option to avoid further discussions about violation of Google policies'. The Offline listing is version '1.14-r0', 'Updated on Sep 20, 2025'.
  - correction: As of 2026-10-06, only 'Keepass2Android Offline' (keepass2android.keepass2android_nonet) is on Google Play, and it is at 1.14-r0 from 2025-09-20, not 1.15-r4. The main app has been missing from Play since about 2026-10-03 and is available only as GitHub APKs. The report's 'Google Play (two apps)' is out of date.
- [corrected] (claim 5) Users report the clipboard not being cleared (#2683, #2488), presented in the brief as open issues.
  - evidence: Both issues are CLOSED. #2683 (2026-09-03) was closed the same day and labelled 'out of scope' with a link to the wiki; its reporter wrote that after reverting to 4.4.5 'the issue persists… the bug might be on my side'. #2488 was filed by the maintainer from the #2480 review, about OTP copies having no timeout, and closed 2026-04-30. The quoted text 'I can still paste said copied credentials even after the 20s clipboard timeout' is a user comment there. The maintainer replied: 'the clipboard timeout doesn't work on many devices.'
  - correction: The complaints are real, but both issues are closed. Neither shows the cause the report infers (comparing the clipboard before clearing it). The maintainer and the wiki blame operating systems and clipboard histories that cannot be cleared.
- [corrected] (claim 5) CSV import was requested in #505 and has been open since 2020.
  - evidence: #505 'Add import from CSV option' is OPEN and was created 2020-03-30. However, the wiki page Import-and-Export says: 'KeePassDX does not and will not offer this plaintext import feature'. Import through the Credential Exchange Format is 'in development' (#2705, opened 2026-09-11; maintainer: 'This will be a must-have feature').
  - correction: The issue is still open, but the maintainer has stated that CSV import will never be added. A non-expert would need a computer (KeePass or KeePassXC) or web converters, or would have to wait for CXF import.

## Missed issues
- Keepass2Android distribution is out of date, and this changes what we tell the user. Since about 2026-10-03 the main app (keepass2android.keepass2android) is not on Google Play: its Play page returns 404 in US, DE, GB and UZ, and the developer's Play page lists only the Offline app and plugins. Issue #3320 reports it missing. Commit 76d8502 (2026-10-05) removes the donate menu 'to avoid further discussions about violation of Google policies'. The Play 'Keepass2Android Offline' listing is at 1.14-r0 ('Updated on Sep 20, 2025'), not 1.15-r4. Section 2 ('Google Play (two apps)') and any advice to install Keepass2Android from Play need rewording.
- KeePassDX's official position on import is stronger than '#505 open'. Its wiki page Import-and-Export says 'KeePassDX does not and will not offer this plaintext import feature' and sends users to KeePass or KeePassXC on a computer, or to web converters. For a non-expert who already has passwords in a browser or Google, this is a real barrier to 'just install KeePassDX'. Recommendation 1 should say so.
- The report missed a relevant standard. Android now has a Credential Transfer API (androidx.credentials:providerevents; group-index lists versions up to 1.0.0-beta01) built on the FIDO Credential Exchange Format (CXF). It supports passwords, passkeys and custom fields, and developer.android.com/identity/sign-in/credential-transfer says it 'works on devices running Android 8 (API level 26) and later'. The KeePassDX maintainer calls CXF import and export 'a must-have feature' (#2705, 2026-09-11). The vault's import and export plan (the report proposes only encrypted export plus KDBX) should at least consider CXF behind an API 26 check, given our minSdk 24. Whether Google Password Manager exports through it was not verified.
- The report's [I] point, 'a hostile file can demand huge memory through unauthenticated KDF parameters', is confirmed by primary evidence it did not cite. KeePassDX #2640 (2026-08-07, labelled security) is titled 'Argon2 KDF cost parameters from the database header are not clamped, enabling denial of service via a crafted .kdbx'. It was fixed in 4.5.0 ('Fix KDF max parameters #2640'): 4.5.5's Argon2Kdf.kt validates ranges and calls checkLimits/isMemorySufficient against device memory. The KDBX spec allows Argon2 memory up to 0x7FFFFFFF bytes and parallelism up to 0x00FFFFFF. 'Lessons for our app' should add: bound KDF parameters read from our own header or from any imported KDBX file, against device RAM, before running Argon2.
- The audit evidence is stronger than the report says. #561 '(Crowd)fund security audit' has been open since 2020-05-20, and the only reviews are user-run, AI-assisted ones (#2480; #2640 names Codex and Kimi). The 'maintainer calls it AI-generated' remark comes from #2488 ('the issue detected by the AI'), not from #2480 itself.
- Section 4's 'Known problems' column lists fixed bugs as if they were current. KeePassJava2 #97 and #98 (attachments duplicated or lost) are CLOSED and fixed in 3.0.0 (2026-10-03). #78 (KeePassXC could not open new files) was fixed in 2.2.4 (2025-03-05). kotpass #8 was closed 2023-09-22 and #38 ('Performance boost') on 2026-07-03. They are valid as history but should carry 'fixed in …' labels.
- Whether KeePassJava2 3.x runs on Android (listed under 'Not settled') has concrete obstacles. Its only remaining back-end uses Jackson and Woodstox with javax.xml.stream (KdbxSerializableDatabase.java imports javax.xml.stream.XMLOutputFactory), and android-37's android.jar and api-versions.xml contain no javax/xml/stream at all. 3.1.0 also switched model times to java.time.Instant, which is API 26+ ('since=26') and would need core-library desugaring at minSdk 24. The README still says 'Android compatible'.
- Palant's 'under-documented' criticism (2023-03-29) is out of date. keepass.info now publishes a complete 'KDBX File Format Specification' ('This specification defines the latest version (4.1)'), which the Wayback CDX first records on 2024-03-14. The report cites that very specification, so it should not list missing documentation as a current weakness. That implementations differ may still be true.
- Another friction for the 'open, see and copy' user is missing. Since 4.3.0, KeePassDX asks for User Verification on every protected field, including viewing or copying a password, unless the user opens the database in UV-disabled mode (since 4.3.1). The wiki also says that without a device screen lock, UV accepts 'the first 4 digits of your password'. The maintainer, in #2321: 'It is not recommended to copy passwords to the clipboard in any case.'
- The clipboard section cites #2683 and #2488 as evidence for the compare-before-clear cause, but neither issue supports it. #2683 was closed as out of scope, and its reporter suspected his own device. The maintainer and the wiki (Clipboard page: 'some devices do not allow to delete any data stored in the clipboard') blame operating systems and clipboard histories. The compare is real (4.5.5 ClipboardHelper.kt:84-85: 'if (getClipboardText() == valueString) cleanClipboard()'), so the design conclusion should rest on the AOSP and code reading and be tested, not on these issues.
- 'Copy PocketVault's key hierarchy' rests on a very young project. It has 16 stars, four releases within one week (v2.4.0 on 2026-08-05 to v2.6.0 on 2026-08-11), about 12 commits in its commit feed, none since 2026-08-12, and a 2.5.0 regression that marked valid vaults as damaged. Wrapping a random vault key twice is a sound, standard pattern, but the report should justify it from documentation and standards rather than present PocketVault's code as a vetted model.
- The [M] note 'Android 16+ may block' PassVault's intent forwarding is now supported by documentation. developer.android.com 'Behavior changes: all apps' for Android 16 says: 'Android 16 provides default security against general Intent redirection attacks' (opt-out: Intent.removeLaunchSecurityProtection()). It can be retagged [P], still unexploited.
- The licence note 'Keyguard and 2FAS Pass permit no reuse' is fully right only for Keyguard ('All Rights Reserved'). 2FAS Pass's BUSL-1.1 LICENSE forbids production use now, but 'Change Date: Two (2) years from the date of release of each version. Change License: GNU General Public License, version 3.0', so older versions will become GPL-3.0 code.
