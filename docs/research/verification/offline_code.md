# Verification: offline (code lens) — independent check, 2026-10-06

## Overall
Within the code-and-artifact lens the report is reliable: I could not refute any of the 11 claims. Every file and line reference I checked in KeePassDX 4.5.5, KeyPass, PassVault, PocketVault, kotpass 0.13.0 (jar and sources from Maven Central) and AOSP android17-release says what the report says. The published KeePassDX APKs match the source: no INTERNET permission, minSdk 19, targetSdk 36, no Compose. Seven sub-claims need correcting before we copy them into code or advice. Of these, the Argon2 and AES-KDF figures are only defaults until KeePassDX benchmarks them, and the auto-lock alarm is usually inexact. Before we rely on the report, fix the design lessons it does not cover: allowBackup=false no longer stops device-to-device transfer at our targetSdk 37, so we need dataExtractionRules, and an unconditional clipboard clear will also wipe the user's own later copies. We also need API-level fallbacks for minSdk 24 and must set kotpass's Argon2id parameters explicitly. Evidence downloaded today is under /tmp/claude-1000/-home-asus-AndroidStudioProjects-PasswordVault/096e95f8-3ae0-41bf-b235-08771bb88852/scratchpad/verify-offline-code/ (apk/, aosp/, kotpass/, lifecycle/).

## Not confirmed
- [corrected] (claim 1) If Argon2 is chosen, its defaults are 16 MiB, 3 iterations, parallelism 4.
  - evidence: The constants exist: Argon2Kdf.kt:248 DEFAULT_ITERATIONS = 3u, :252 DEFAULT_MEMORY 16 MiB, :257 DEFAULT_PARALLELISM = 4u. However, choosing a KDF in settings calls DatabaseKeyDerivationPreferenceDialogFragmentCompat.onDialogClosed, then saveKeyDerivation, then UpdateKeyDerivationDatabaseRunnable.kt:53-63: `if (newKeyDerivation.isDefault()) { ... optimizeByBenchmark(masterKey, limits = context.getKdfLimits()) }`. KdfEngine.calculateBenchmark (KdfEngine.kt:68-106) sets parallelism to limits.parallelism, which is Runtime.availableProcessors() (AppUtil.kt:252-254), and memory to min(limits.memory, defaultMemoryUsage), where limits.memory is 3/4 of available RAM (Limits.kt:52). It then rescales iterations to DEFAULT_BENCHMARK_TIME = 1000 ms (KdfEngine.kt:221).
  - correction: 3 iterations and parallelism 4 are only the pre-benchmark constants. After the user picks Argon2d or Argon2id, KeePassDX stores memory = 16 MiB (lower only on low-RAM devices), parallelism = the number of CPU cores, and an iteration count benchmarked to about 1 s on that phone. The switch also makes the file KDBX 4.0. Memory stays at 16 MiB unless the user raises it.
- [corrected] (claim 1) AES-KDF defaults to 500,000 rounds.
  - evidence: AesKdf.kt:94 `override val defaultKeyRounds: ULong = 500_000u`. CreateDatabaseRunnable.kt:67-98 then calls kdfEngine.randomize() and kdfEngine.optimizeByBenchmark(masterKey, limits) before the first save, which rescales rounds to the 1000 ms target (KdfEngine.kt:85-91, 114-124).
  - correction: 500,000 is the class default. A database created in the app is written with however many rounds take about 1 s on that phone, not 500,000. Report section 3 already says '500,000 rounds, then a 1 s benchmark'.
- [corrected] (claim 3) allowBackup="true" with backup rules excluding the cipher_database table.
  - evidence: Manifest :63 allowBackup="true" (the APK xmltree also shows allowBackup=true), :64 fullBackupContent=@xml/old_backup_rules, :65 dataExtractionRules=@xml/backup_rules, :66 backupAgent=SettingsBackupAgent, and no fullBackupOnly. backup_rules.xml:21-30 includes domain sharedpref '.' and domain database '.', and excludes domain database path `com.kunzisoft.keepass.database`. That path is the whole Room file (AppDatabase.kt:44-47), which holds both cipher_database and file_database_history. SettingsBackupAgent backs up only `<package>_preferences`. AOSP android17 BackupEligibilityRules.appGetsFullBackup: 'If it has an agent, it gets full backups only if it says so' (FLAG_FULL_BACKUP_ONLY).
  - correction: The rules exclude the entire Room database file com.kunzisoft.keepass.database (cipher_database and the recent-files history), not one table. Because the app declares a key/value backupAgent without fullBackupOnly, Android backs it up through SettingsBackupAgent, which copies only the default SharedPreferences. The XML rules apply only to full-data backup. Either way, the stored biometric credential is not backed up.
- [corrected] (claim 4) It uses an AlarmManager.setExact broadcast plus a saved wall-clock timestamp checked on resume.
  - evidence: TimeoutHelper.kt:60-85: triggerTime = System.currentTimeMillis() + timeout. On API 31+ with `!alarmManager.canScheduleExactAlarms()` it calls `alarmManager.set(AlarmManager.RTC, ...)`; otherwise it calls `setExact(AlarmManager.RTC, ...)`. Both are non-wakeup RTC alarms. AOSP android17 AlarmManager.java:296-304: SCHEDULE_EXACT_ALARM_DENIED_BY_DEFAULT, @EnabledSince(TIRAMISU), 'will be denied, unless the user explicitly allows it from Settings'. The wall-clock part is right: PreferencesUtil.saveCurrentTime (:445-450) stores System.currentTimeMillis(), and TimeoutHelper.checkTime (:117-148) compares against it. checkTime runs from DatabaseLockActivity when the database is retrieved on start (:141), in onPause (:352), and on touch/focus (:407-427).
  - correction: The 5-minute lock uses AlarmManager.setExact(RTC) only when exact alarms are permitted. For KeePassDX (targetSdk 36) SCHEDULE_EXACT_ALARM is denied by default unless the user grants it, so the usual path is the inexact AlarmManager.set(RTC). Both alarms are non-wakeup. The lock is enforced reliably by the System.currentTimeMillis() timestamp check, which runs when an activity starts, pauses or is touched.
- [corrected] (claim 7) The system clears the clipboard after DEFAULT_CLIPBOARD_TIMEOUT_MILLIS = 3600000.
  - evidence: android17-release :143 `public static final long DEFAULT_CLIPBOARD_TIMEOUT_MILLIS = 3600000;`. scheduleAutoClear (:623-645) runs only if DeviceConfig PROPERTY_AUTO_CLEAR_ENABLED (default true), and getTimeoutForAutoClear (:647-651) reads DeviceConfig PROPERTY_AUTO_CLEAR_TIMEOUT with 3600000 as the default. scheduleAutoClear is called on every set (:618) and again on every getPrimaryClip (:711). The constant exists in android13-release but not in android12-release or 12L. The local copy the report used (offline/aosp/ClipboardService.java, sha256 c78968f8…) is byte-identical to refs/heads/main, not android17-release (8bdf17a9…); the values are the same in both.
  - correction: The system auto-clears one hour (a DeviceConfig default that can be changed remotely or switched off) after the clip was last set or read by any app, because every read resets the timer. This exists only on Android 13+. On Android 7-12 (inside our minSdk 24 range) there is no system clear at all.

## Missed issues
- The lesson `allowBackup="false"` (and checklist item 8, which counts allowBackup="true" as a mistake) does not do what the report assumes for an app with targetSdk 37. AOSP android17-release BackupEligibilityRules.java:115-122 says: 'When this change is enabled, android:allowBackup is ignored for apps during D2D (device-to-device) migrations', with IGNORE_ALLOW_BACKUP_IN_D2D @EnabledSince(targetSdkVersion = S). isAppBackupAllowed (:254-265) returns true for any non-system app during DEVICE_TRANSFER. Our vault file will therefore be copied to a new phone during setup transfer unless android:dataExtractionRules has a <device-transfer> exclude. Keystore keys do not travel, so we must also decide deliberately: either exclude the vault, or allow the password-wrapped vault to migrate. If it migrates, a failed biometric unwrap on the new phone must be treated as 'biometric off', never as a reason to delete data.
- The recommended 'unconditional timed clearPrimaryClip(), no compare-read' has a cost the report does not state. A backgrounded app can neither read the clipboard nor learn that it changed: ClipboardService.sendClipChangedBroadcast (android17 :1092-1110) notifies listeners only if clipboardAccessAllowed(OP_READ_CLIPBOARD) passes. So an unconditional clear after N seconds will also erase whatever the user copied later in another app; this trade-off should be stated in the design. The minSdk 24 version matrix is also missing. clearPrimaryClip is API 28+ (api-versions.xml), so API 24-27 need setPrimaryClip(empty), as KeePassDX and PocketVault do. EXTRA_IS_SENSITIVE is an API 33 constant: use the literal key below 33, and older system UIs ignore it. Background reads are allowed on Android 7-9 (pie-release: 'Installed apps can access the clipboard at any time'). The system one-hour auto-clear exists only on Android 13+ and restarts on every read.
- The advice 'the user should switch to Argon2id in the database settings' in KeePassDX leaves memory at 16 MiB. UpdateKeyDerivationDatabaseRunnable.kt:53-63 together with KdfEngine.calculateBenchmark (:68-106) caps memory at the 16 MiB default and spends the 1 s budget on extra iterations (parallelism = number of cores). To get the memory-hardness the report wants, the user would also have to raise 'Memory usage' manually, for example to 64 MiB, the KeePassXC default ARGON2_DEFAULT_MEMORY = 1<<16 KiB in Argon2Kdf.h:25. The switch also turns the file into KDBX 4.0 (getMinKdbxVersion, kdfIsNotAes).
- Checklist item 4 ('a key silently created on a decrypt path') names only PassVault, but KeePassDX does the same. DeviceUnlockManager.getSecretKey (:91-147) creates the key whenever the alias is missing, including from initDecryptData. On UnrecoverableKeyException the decrypt path deletes the key and re-initialises with a fresh one (:269-276). On KeyPermanentlyInvalidatedException it wipes the stored credentials for all databases (CipherDatabaseDao 'DELETE FROM cipher_database'), not only the current database's.
- The PassVault note 'Android 16+ may block it [M]' can be backed with source and made more precise. android17-release Intent.java (removeLaunchSecurityProtection javadoc) says: 'If this token is missing or invalid, the system will block the launch of this intent... block launching target it has no permission to launch or block it from granting URI access'. ActivityStarter.java:658-720 and :1333-1365 enforce this. The compat change ENABLE_PREVENT_INTENT_REDIRECT_TAKE_ACTION (:190-192) is @Overridable with no @EnabledSince, so it does not depend on targetSdk. AOSP build/release (android17-release) aconfig/bp2a/android.security sets prevent_intent_redirect and prevent_intent_redirect_abort_or_throw_exception to ENABLED. api-versions.xml has Intent.removeLaunchSecurityProtection since="36". The redirect therefore still works on PassVault's Android 9-15 devices (minSdk 28) and on builds where those flags are off.
- There are kotpass packaging and default traps the export plan needs to know about. The 0.13.0 jar ships Apache-2.0 org.apache.commons.lang3.* and org.redundent.kotlin.xml.* classes in their original packages, which risks a 'Duplicate class' build failure if any dependency brings the real commons-lang3. It also adds Apache NOTICE and Bouncy Castle licence obligations on top of MIT. Ver4x.create defaults to Argon2d, 32 MiB, t=8, p=2 (KdfParameters.kt:89-99), so our exporter must set Argon2id parameters explicitly. AesKdf.transformKey uses `repeat(rounds.toInt())` and Argon2Kdf uses `memory.toInt() / 1024`, both of which overflow on extreme header values. That only matters when reading foreign or hostile files, but it is another reason to keep kotpass to export only.
- KeePassDX auto-lock is less exact than the report implies. SCHEDULE_EXACT_ALARM is denied by default for apps targeting 33+ (AOSP AlarmManager.java:296-304), so TimeoutHelper normally falls back to an inexact, non-wakeup AlarmManager.set(RTC). The wall-clock check when an activity starts or is touched is what actually enforces the lock. This supports the report's lesson to use elapsedRealtime plus a check on return to the foreground, and argues against relying on AlarmManager for our lock.
- Provenance: the earlier agent's AOSP ClipboardService copy (offline/aosp/ClipboardService.java, 1634 lines, sha256 c78968f8…) is byte-identical to refs/heads/main, not android17-release (1787 lines, sha256 8bdf17a9…). The cited facts are the same in both, but any line numbers taken from the local file will not match android17-release.
