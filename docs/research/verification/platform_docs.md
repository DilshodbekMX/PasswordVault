# Verification: platform (docs lens) — independent check, 2026-10-06

## Overall
Within my lens (versions, dates, documentation, standards, audits), the report holds up well. Every DAC, AOSP, Maven, paper, advisory and NVD source I opened today says what the report says, and every API level I checked matches api-versions.xml. The version figures are current: BOM 2026.09.00 maps to ui/foundation 1.12.1 and material3 1.4.0; biometric 1.1.0 is from January 2021 and 1.4.0-alpha07 from 22 April 2026; core is at 1.19.1; Bitwarden is at 2026.9.1, KeePassDX at 4.5.5 and Proton Pass at 1.41.2. Before we build on it, these need fixing: (1) the clipboard-clear scheduling facts (inexact alarms have no one-hour bound under Doze or battery saver, and listener exact alarms are dropped once the app is cached); (2) the backup rules (on Android 12+ D2D ignores allowBackup and fullBackupContent in AOSP, a missing cloud section falls back to the legacy rules, a third cross-platform section exists, and the allowBackup value must be stated explicitly); (3) smaller precision fixes: the biometric shim exists from 1.4.0-alpha05, the predictive-back opt-out still exists at target 37, Android 17's memory limits and IME change apply to all apps, and StrandHogg 2 needs the OS patch, so minSdk 24 leaves old phones exposed. Evidence is saved under VP=/tmp/claude-1000/-home-asus-AndroidStudioProjects-PasswordVault/096e95f8-3ae0-41bf-b235-08771bb88852/scratchpad/verify-platform-docs (dac/, aosp/, aar/, maven/, threats/, teamsik/).

## Not confirmed
- [corrected] (claim 1) App memory limits are introduced (presented as a target-37 change).
  - evidence: This is on the all-apps page, not the target-37 page. VP/dac/bc17_all.txt:23-25: 'Android 17 introduces app memory limits based on the device's total RAM ...'. A session that was cut short ends with REASON_OTHER, and its description contains 'MemoryLimiter:AnonSwap'. Lines 31-47 describe the adb commands 'am memory-limiter ignore|manual|status'.
  - correction: The limits apply to every app running on Android 17, whatever its targetSdk. No number is published; the limit depends on the device's RAM. To test the KDF memory setting, run 'adb shell am memory-limiter manual <pid> <MB>' and then check ApplicationExitInfo.
- [corrected] (claim 1) The keyboard is not restored after rotation (presented as a target-37 change).
  - evidence: VP/dac/bc17_all.txt:162-169 (all-apps page): 'when the device's configuration changes (for example, through rotation), and this is not handled by the app itself, the previous IME visibility is not restored.' The documented fixes are windowSoftInputMode=stateAlwaysVisible, or requesting the keyboard in onCreate()/onConfigurationChanged().
  - correction: This applies to all apps on Android 17, whatever their target, and only when the app does not handle the configuration change itself.
- [corrected] (claim 4) On Android 12+ an inexact alarm set with AlarmManager.set() is delivered within one hour of the requested time.
  - evidence: DAC /develop/background-work/services/alarms (VP/dac/alarms.txt:45-47; the cited path .../alarms/schedule now 301-redirects here): 'If your app calls set(), setInexactRepeating(), or setAndAllowWhileIdle(), the alarm never goes off before the supplied trigger time. On Android 12 (API level 31) and higher, the system invokes the alarm within one hour of the supplied trigger time, unless any battery-saving restrictions are in effect such as battery saver or Doze.' AOSP AlarmManagerService.java:1438-1457 caps the delivery window for non-repeating alarms at triggerAtTime + INTERVAL_HOUR.
  - correction: The one-hour bound holds only when no battery-saving restriction applies. Under Doze or battery saver the alarm can be later than one hour, and it never fires early. The report's 'may fire up to an hour late' needs that qualifier.
- [corrected] (claim 4) USE_EXACT_ALARM (API 33) is intended only for alarm-clock and calendar apps.
  - evidence: api-versions.xml and the Manifest.permission reference: 'Added in API level 33'. The platform text (Manifest.permission reference; AOSP core/res AndroidManifest.xml:6890-6916; protectionLevel normal) says: 'This is only intended for use by apps that rely on exact alarms for their core functionality.' The Android 14 page (VP/dac/a14_exact_alarms.txt:37-41) says 'Calendar or alarm clock apps ... can request the USE_EXACT_ALARM normal permission' and 'Apps will not be able to publish a version of their app with this permission in the manifest unless they qualify based on the policy language.' The Google Play policy (support.google.com/googleplay/android-developer/answer/9888170, VP/dac/play_9888170.txt:318-321) lists 'The app is an alarm or timer app' and 'The app is a calendar app that shows event notifications.'
  - correction: API 33 is correct. The platform grants USE_EXACT_ALARM at install to any app that targets 33 or higher and declares it; it is a normal permission, intended for apps whose core function needs exact alarms. The restriction to alarm or timer apps and calendar apps is Google Play policy, which also allows timer apps. A password vault would not qualify on Play. The report itself never mentions USE_EXACT_ALARM.
- [corrected] (claim 5) dataExtractionRules has separate cloud-backup and device-transfer sections, and a missing section means that mode is fully enabled.
  - evidence: VP/dac/autobackup.txt:303: 'If there are no rules for a particular backup mode, such as if the <device-transfer> section is missing, that mode is fully enabled for all content except for no-backup and cache directories'. The same page (lines 108, 285-301, 364) documents a third section, <cross-platform-transfer platform="ios">, available 'from Android 16 QPR2'. AOSP FullBackup.java:122-129 lists all three sections. In parseSchemeForBackupDestination (lines 646-690), a missing section falls back to android:fullBackupContent, except for D2D: IGNORE_FULL_BACKUP_CONTENT_IN_D2D (lines 112-119, @EnabledSince S) means D2D with no section transfers everything. BackupEligibilityRules.java:313-316 allows cross-platform transfer only when allowBackup is set and the app has opted in.
  - correction: There are now three sections. With no <device-transfer> section, D2D copies everything except no_backup and cache, because the legacy rules are ignored for D2D at target 31+. With no <cloud-backup> section, cloud backup falls back to the fullBackupContent rules if they exist, and is fully enabled only if they do not. With no <cross-platform-transfer> section, iOS transfer is off. Write the cloud and device sections explicitly.
- [corrected] (claim 6) Google's stated fix for StrandHogg is minSdkVersion 30, with taskAffinity and launch mode only partial mitigations.
  - evidence: DAC /privacy-and-security/risks/strandhogg (VP/dac/strandhogg.txt:39-41): 'Update to android:minSdkVersion="30".' ... 'While it is possible to partially mitigate version 1 of the StrandHogg attack through individual application configuration, version 2 of the attack can only be prevented by this SDK version patch.'
  - correction: The page says 'individual application configuration' and does not name taskAffinity or launchMode. More importantly, app configuration can only partly mitigate version 1 and does nothing against version 2, which only the Android 11 (SDK 30) OS patch prevents. With minSdk 24, the vault stays exposed to StrandHogg 2 on unpatched Android 7 to 10 devices.
- [corrected] (claim 7) Mark sensitive clips with ClipDescription.EXTRA_IS_SENSITIVE on API 33+, and with the literal extra name 'android.content.extra.IS_SENSITIVE' below.
  - evidence: DAC secure-clipboard-handling (VP/dac/clip_secure.txt:40-64) and the copy-paste guide split the two forms by compile SDK: '// If your app is compiled with the API level 33 SDK or higher' uses the constant, and '// If your app is compiled with API level 32 SDK or lower' uses the literal. javap on the android-37 android.jar shows EXTRA_IS_SENSITIVE = "android.content.extra.IS_SENSITIVE" (a compile-time constant), and ClipDescription.setExtras is API 24.
  - correction: The choice depends on the compile SDK, not the device's API level. With compileSdk 37 the constant is inlined, so it works on every runtime level from API 24 up. The report's table states this correctly; only this summary of it is wrong.
- [corrected] (claim 7) (Secure clipboard page) Android 13+ shows a visual confirmation when content is copied, so apps should not show their own.
  - evidence: The statement is not on /privacy-and-security/risks/secure-clipboard-handling. It is in the copy-paste guide /develop/ui/views/touch-and-input/copy-paste (VP/dac/copy_paste.txt:263): 'Starting in Android 13, the system displays a standard visual confirmation when content is added to the clipboard'. Line 275: 'we strongly recommend removing toasts or snackbars shown after an in-app copy for Android 13 and higher.'
  - correction: The content is correct, but the source is the copy-paste guide, not the secure clipboard handling page.
- [corrected] (claim 9) The androidx.core release notes for 1.18.0 describe the FingerprintManagerCompat change (deprecated and made to do nothing).
  - evidence: Core release notes (VP/dac/rel_core.txt:268): under 1.18.0-alpha01 (14 January 2026), Bug Fixes: 'Removed references to FingerprintManager class from FingerprintManagerCompat and updated all methods to return false or no-op. (I0360b,b/330524057)'. The 1.18.0 stable entry (11 March 2026, lines 199-210) does not mention it. The class had already been 'soft-removed' and deprecated in 1.13.0 (lines 489, 511). javap shows that core 1.17.0 still calls FingerprintManager, while in 1.18.0 and 1.19.1 isHardwareDetected/hasEnrolledFingerprints are 'iconst_0; ireturn' and authenticate is 'return'. Both classes already carry @Deprecated and @RestrictTo in 1.17.0. The AAR sha256 matches Google Maven.
  - correction: The no-op change shipped in the 1.18.0 line (first in 1.18.0-alpha01, 14 January 2026). The deprecation is older: 1.13.0 (April 2024). The wording 'Deprecate ... now is a no-op' appears in the biometric 1.4.0-alpha05 release notes (17 December 2025), not in the core notes. The latest core, 1.19.1 (23 September 2026), is still a no-op.

## Missed issues
- Clipboard-clear scheduling misses a key fact: listener-based exact alarms need no permission, but Android drops them once the app is cached. The DAC alarms page (VP/dac/alarms.txt:163) says: 'If the exact alarm is set using an OnAlarmListener object, such as with the setExact API, the SCHEDULE_EXACT_ALARM permission isn't required.' AOSP android17-release AlarmManager.java:317-324 says: 'Exact alarms expecting a OnAlarmListener callback will be dropped when the calling app goes into cached state' (EXACT_LISTENER_ALARMS_DROPPED_ON_CACHED, not gated on target SDK). AlarmManagerService.java:1880-1900 removes them from a UidFrozenStateChangedCallback. The report lists 'setExactAndAllowWhileIdle with a listener' as new in API 37 without saying it cannot clear the clipboard after the user leaves the app, and its 'exact alarms need a special access' does not apply to listener alarms. Only PendingIntent alarms and WorkManager survive the app going to the background.
- The 'Not settled' option 'inexact alarm (up to an hour late)' treats a conditional bound as a guarantee. The DAC (VP/dac/alarms.txt:47) says: 'within one hour of the supplied trigger time, unless any battery-saving restrictions are in effect such as battery saver or Doze.' The clear-timing decision and the user-facing wording should not promise one hour.
- Backup and D2D control is wider than the report says, and the vault rules depend on it. In AOSP android17-release, BackupEligibilityRules.java:115-122 and 255-267 ignore allowBackup for device-to-device transfer for every non-system app that targets 31 or higher (IGNORE_ALLOW_BACKUP_IN_D2D). FullBackup.java:112-119 and 677-681 likewise skip fullBackupContent rules for D2D (IGNORE_FULL_BACKUP_CONTENT_IN_D2D). On Android 12+ the <device-transfer> section is therefore the only control on any AOSP-based device, not only on 'some manufacturers' devices'. On Android 7 to 11, allowBackup=false blocks D2D completely. The report's 'Right setting for us' never states the allowBackup value, and that value decides whether 'optional device-to-device transfer of the vault file' works on Android 7 to 11.
- The data-extraction-rules description is out of date. The Auto Backup page (VP/dac/autobackup.txt:108, 285-301, 364) adds a third section, <cross-platform-transfer platform="ios">, available from Android 16 QPR2 (API 36.1); AOSP FullBackup.java:122-129 parses it. It is opt-in, requiring allowBackup and platform-specific params (BackupEligibilityRules.java:313-316), so leaving it out is safe. Also, AOSP falls back to fullBackupContent when <cloud-backup> is missing (FullBackup.java:646-690), so 'a missing section means fully enabled' holds only for D2D. Both sections should be written explicitly.
- Biometric version facts are slightly off. The androidx.biometric release notes for 1.4.0-alpha05 (17 December 2025; VP/dac/rel_biometric.txt:118) say core's FingerprintManagerCompat 'now is a no-op' and that 'A new internal androidx.biometric.FingerprintManagerCompat is used'. An AAR check today (Google Maven) shows 1.4.0-alpha04 calling core's class from 6 classes, while 1.4.0-alpha05, -alpha06 and -alpha07 call it from none. The shim therefore exists since alpha05, not 'only 1.4.0-alpha07'. The conclusion stands: 1.1.0 (KeePassDX) and 1.2.0-alpha05 (Bitwarden, Proton) still call the class that is a no-op from core 1.18.0, and the latest core, 1.19.1, is unchanged.
- Two official biometric pages disagree on what works below API 28. The guide /identity/sign-in/biometric-auth (VP/dac/biometric_guide.txt:69) says DEVICE_CREDENTIAL and BIOMETRIC_STRONG|DEVICE_CREDENTIAL 'aren't supported on Android 10 (API level 29) and lower'. The PromptInfo.Builder reference and the library bytecode (AuthenticatorUtils.isSupportedCombination in 1.1.0 and 1.4.0-alpha07) reject STRONG|DEVICE_CREDENTIAL only on API 28 and 29 and accept it below 28. With minSdk 24, follow the reference and the bytecode, and test on API 24 to 27.
- Section 1 item 10 is wrong to say predictive back is 'enforced at target 37'. The opt-out is still documented (predictive-back guide: 'To opt out ... set the android:enableOnBackInvokedCallback flag to false'; application-element doc), no Android 17 behaviour-change page removes it, and Android 17 still honours it (AOSP WindowOnBackInvokedDispatcher.java:791-826). Only edge-to-edge (opt-out disabled at 36) and large-screen orientation and resizability (opt-out gone at 37) are actually enforced. The design advice (use BackHandler) is unaffected.
- The threat model leaves out task hijacking on old phones. The StrandHogg page (VP/dac/strandhogg.txt:41) says app configuration only 'partially mitigate[s] version 1' and 'version 2 of the attack can only be prevented by this SDK version patch'. With minSdk 24, the vault runs on Android 7 to 10 devices where only the OS patch helps. Like TapTrap (fixed only on Android 13 to 16) and GPU side channels, this belongs in the 'we do not defend against' list or the minimum-version decision.
- The vulnerability history misses a 2025 example of the package-name pitfall. Bitwarden's audit page now also links a 2025 Mobile App Security Assessment (Unit 42, dated 23 October 2025; VP/threats/bw2025_mobile.txt). Its finding M.1, 'Insufficient Package Name Validation Allows TOTP Secret Harvesting (Medium)', was fixed by replacing 'package-name based trust with certificate fingerprint validation'. The report supports its autofill and package-name argument only with 2016 to 2018 sources, plus the Cure53 2024 report.
- One fact for the user advice: Gboard keeps its own clipboard history and lets users pin items. The Gboard help page (support.google.com/gboard/answer/10742542, fetched today) says: 'The clipboard clears your history shortly after you last use it. This doesn't apply to pinned text.' A pinned copied password survives both our clear and Android's one-hour auto-clear. The user should be told never to pin passwords.
- A new 16 KB deadline applies if a native KDF library is chosen. The page-sizes guide (developer.android.com/guide/practices/page-sizes, fetched today) says: 'Starting February 1, 2027, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates' on Google Play. The report's 'pure Kotlin already is' covers only JVM code; a native Argon2 or libsodium library must be checked for 16 KB alignment.
