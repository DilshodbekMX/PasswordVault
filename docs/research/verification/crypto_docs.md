# Verification: crypto (docs lens) — independent check, 2026-10-06

## Overall
Within my lens the report is accurate. Every listed figure checks out against primary sources fetched today: OWASP, RFC 9106, NIST 63B-4 and 38D, the Android Cipher, SecretKeyFactory, KeyProperties and KeyGenParameterSpec docs, CDD 7.0/16/17, the EFF list and licence, Maven dates and licences, hashcat, the gist, Hugenroth, 1Password, Bitwarden and #7436. Its Argon2id test vector reproduces exactly with BC 1.86 from Maven and with freshly built PHC reference C, and BC also reproduces the RFC 9106 §5.3 Argon2id tag. Before relying on it, fix five things. Specify NIST's stabilized-string NFC (reject unassigned code points) and note that NIST's 15-character rule covers centrally verified passwords. Re-justify or gate the 64 MiB Bouncy Castle heap fallback against the CDD heap minimums and Aegis's OOM note. Correct the Bitwarden InsufficientKdfParameters precedent, since it is a lower bound. Call #7436 a closed single report with no code fix. Add the EFF CC BY 4.0 attribution duty.

## Not confirmed
- [corrected] (claim 3) NIST: apply NFC before hashing.
  - evidence: §3.1.1.2 (PDF p.15): "If Unicode characters are accepted in passwords, the verifier SHOULD apply the normalization process for stabilized strings using the Normalization Form Canonical Composition (NFC) normalization defined in Sec. 12.1 of Unicode Normalization Forms [UAX15]. This process is applied before hashing the byte string that represents the password." UAX #15 §12.1 (unicode.org/reports/tr15): the Normalization Process for Stabilized Strings must "be aborted with an error if the string contains any code point with the property value General_Category=Unassigned".
  - correction: NIST names the Normalization Process for Stabilized Strings applied with NFC (UAX #15 §12.1), as a SHOULD, before hashing. That process is NFC plus rejecting any code point unassigned in the running Unicode version. A plain java.text.Normalizer NFC call does not do the second part.
- [corrected] (claim 12) Bitwarden help page: PBKDF2 600,000 default, with an Argon2id option of 64 MiB or 32 MiB.
  - evidence: bitwarden.com/help/kdf-algorithms/: "For PBKDF2 SHA-256, the default KDF iteration setting is 600,000" and "For Argon2id, the default settings are: KDF memory: 32, KDF iterations: 6, KDF parallelism: 4" ("allocate 32 MiB of memory, iterate over it 6 times ... across 4 threads"). 64 MiB appears only in: "Argon2id users with a KDF memory value higher than 64 MiB will receive a warning dialogue every time iOS autofill is initiated". The page also says release 2026.2.1 raised the PBKDF2 minimum to 600,000. sdk-internal kdf.rs:163-178 matches (600_000; 6; 32; 4). The 64 MiB/3/4 figure is the separate local envelope preset outside iOS (password_protected_key_envelope.rs:441-464), as the report says.
  - correction: The help page's current defaults are PBKDF2-HMAC-SHA256 at 600,000, or Argon2id at 32 MiB, t=6, p=4. There is no 64 MiB default. The report's own table (32 MiB, t=6, p=4) is right.

## Missed issues
- Normalisation is under-specified. NIST names the Normalization Process for Stabilized Strings with NFC (SP 800-63B-4 §3.1.1.2). Under UAX #15 §12.1 that process "must be aborted with an error if the string contains any code point with the property value General_Category=Unassigned". The report says only "UTF-8 of the NFC-normalised password". In a local vault the key comes from those bytes, so the stabilized-string check is what guarantees an OS or ICU update can never re-normalise a password and lock the user out. Reject code points where Character.getType is UNASSIGNED, and pin the encoding with test vectors.
- NIST scope is overstated. SP 800-63B-4 §3.1.1 says its requirements "apply to centrally verified passwords ... sent over an authenticated protected channel to the verifier". Locally used passwords are 'activation secrets' (§3.2.10: "at least four characters ... SHOULD ... at least six"). The 15-character minimum and the NFC SHOULD are good analogies for our vault, not binding rules. Say so when advising the user.
- The fallback recommendation does not follow from the evidence the report cites. CDD 7.0, 16 and 17 guarantee a normal-screen app only 48 MB (hdpi) or 80 MB (xhdpi) of heap, and never mention largeHeap. Aegis's docs/vault.md says that, with android:largeHeap="true" already in its manifest, raising its 32 MiB Java scrypt runs "into OOM conditions on most devices". A Bouncy Castle fallback that must hold about 64 MiB of Argon2 blocks on the Java heap will therefore fail on many low-end phones. Those are the same phones where argon2kt's loader fails: issue #25 was 86% Transsion/Unisoc and 14% Huawei, and the maintainer wrote "There should be no difference between version 1.6.0 and 1.5.0". §1 presents BC as the runtime fallback without this caveat. At minimum, check ActivityManager.getLargeMemoryClass() or Runtime.maxMemory() first and show a clear error. Also load argon2kt with a custom SoLoader (ReLinker or Facebook SoLoader, as the README and maintainer suggest).
- The precedent for capping KDF parameters is mis-cited. Bitwarden's InsufficientKdfParameters is a lower bound only: sdk-internal kdf.rs:12-16 defines PBKDF2_MIN_ITERATIONS 5000 and ARGON2ID_MIN_MEMORY 16 MiB, iterations ≥2, parallelism ≥1, and lines 39-40 and 58-62 reject values below them. It does not cap attacker-chosen memory or passes. KeePassDX and age ("SHOULD apply an upper limit to the work factor", age.md:335) are the valid precedents for upper bounds. The report's own 65,536-262,144 KiB and t 3-10 bounds are still sound.
- Bitwarden #7436 status has changed. It was closed as COMPLETED on 2026-10-01 with no linked PR. The reason given: the reporter could no longer reproduce after a reboot and an update to 2026.9.0. The delete-first code at PreferenceModule.kt:72-83 is unchanged at HEAD. When comparing apps for the user, call it a single user report, closed without a code fix, not a confirmed open bug.
- The EFF licence brings obligations the report omits. CC BY 4.0 requires attribution and a link to the licence, plus an indication of changes. Filtering the four hyphenated words, as Bitwarden does and as we may need to with a hyphen separator, is a change. The app's About/licences screen must credit EFF. EFF's copyright page also links a CC BY 3.0 US badge next to its 4.0 text. The report did not notice the mismatch; the text governs.
- There is a primary source for the attacker figure, and it shows the figure is a floor. hashcat's own v7.0.0 release notes give 1,703 H/s for an RTX 4090 at m=65536, t=3, p=1 (and 1,367 H/s for an RX 7900 XTX). The report cites Wikipedia. hashcat's unreleased master changelog says "Argon2 buffers now follow attack size rather than self-test size, permitting higher acceleration". OWASP adds: "increasing parallelism is not a guarantee of slower password guessing". So our p=4 should be assumed to give the attacker the same rate as p=1.
- A comparison fact for the user is missing. Aegis's default scrypt N=2^15, r=8, p=1 is below OWASP's current scrypt minimum: at N=2^15 OWASP requires p=3, or N=2^17 with p=1 (cheat sheet lines 126-130). Bitwarden's Argon2id 32 MiB/6/4, its PBKDF2 600,000 and 1Password's 650,000 all meet OWASP's figures. KeePassDX's Argon2 option 16 MiB/t=3 meets OWASP's 12 MiB/t=3 entry.
- The default departs from the cited source. The report makes five words (64.6 bits) the default, while EFF says "For most uses, we recommend ... a six-word passphrase" (77 bits). The departure is defensible given Argon2id's cost (about 2.6×10^8 single-4090 years on average for five words). It is the report's own judgement, and the user should be told that EFF says six.
- There is a stale-library risk for biometric unlock. Stable androidx.biometric 1.1.0 dates from 2021 and its manifest declares targetSdkVersion 30. It lacks fixes that shipped only in the 1.4 alphas: "Update UI to be consistent with platform changes in Android 15" (alpha01), "Fixed error code inconsistencies for disabling biometric app auth on API 34/35", and BiometricPrompt not dismissed on the home button (alpha03). Bitwarden and Proton Pass both use 1.2.0-alpha05 from 2022 instead. 'Aegis ships 1.1.0 at target 36' is only inference that it works on API 37. Plan a device test.
- Minor citation updates. The report cites CDD 7.0 and 16, but CDD 17 (updated 2026-08-31) is the one for compileSdk/targetSdk 37; its values are identical. The KeyGenParameterSpec line numbers (964-978) are from AOSP main; at android17-release the same defaults are at lines 1028-1042. The page-sizes guide says apps targeting API 35+ "must support 16 KB" already; 2027-02-01 is only the cut-off for releasing updates.
