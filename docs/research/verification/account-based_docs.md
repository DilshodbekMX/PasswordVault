# Verification: account-based (docs lens) — independent check, 2026-10-06

## Overall
Within my lens, the report holds up well. Every licence, release version and date (except Padloc's), star count, Play rating, Bitwarden price and plan, audit date and count, offline-session limit, feature-request date and npm-incident detail matches a primary source I opened today. Before we rely on it, fix these: the Issue 6 wording (it is the icon-URL leak; field swapping is the paper's BW05); the Vaultwarden requirements (Docker is recommended, not required; HTTPS is required, a public domain is not); the providerevents library, now 1.0.0-beta01 rather than alpha; the Padloc release date; and the Google Password Manager section, which needs Google's plan to enable non-removable on-device encryption for everyone and its inconsistent export labels. The Recurity 'Medium' rating for SQLite and WAL leftovers rests only on a secondary source: the primary report is in an encrypted Proton Drive share, and my attempt to fetch it was blocked by the permission system. My downloads are under /tmp/claude-1000/-home-asus-AndroidStudioProjects-PasswordVault/096e95f8-3ae0-41bf-b235-08771bb88852/scratchpad/verify-account-based-docs/.

## Not confirmed
- [corrected] (claim 1) Bitwarden's SDK is GPL-3.0 or the Bitwarden SDK Licence.
  - evidence: sdk-internal/LICENSE: 'The default license throughout the repository is your choice of GPL v3.0 OR BITWARDEN SOFTWARE DEVELOPMENT KIT LICENSE unless the header specifies another license. Anything contained within a directory named bitwarden_license is covered solely by the BITWARDEN SOFTWARE DEVELOPMENT KIT LICENSE.' crates/bitwarden-uniffi/Cargo.toml:12 has license = "GPL-3.0-only OR LicenseRef-Bitwarden-SDK". The crates bitwarden_license/{bitwarden-commercial-vault, bitwarden-pam, bitwarden-sm, bitwarden-access-connector} point to LICENSE_SDK.txt. LICENSE_SDK.txt is 'Version 2, 7 October 2025', and clause 1.3 limits use to a 'Compatible Application' that 'connects to and interoperates with' Bitwarden server products.
  - correction: Most SDK crates are 'GPL-3.0-only OR Bitwarden SDK License v2.0'. Code under bitwarden_license/ is covered only by the SDK licence, which is not open source. That licence allows use only in apps that talk to Bitwarden servers, so for a local-only app the GPL-3.0-only route is the only one.
- [corrected] (claim 2) Padloc's last release was on 2023-04-28.
  - evidence: github.com/padloc/padloc/releases/tag/v4.3.0 (Latest) reads 'github-actions released this' with datetime 2023-03-06T16:05:49Z. All 46 assets, including padloc_4.3.0_android.apk, were uploaded on 2023-03-06 between 16:05 and 16:21Z (expanded_assets page). The date 2023-04-28T07:07:11Z appears only as the entry's <updated> value in releases.atom. The Google Play listing app.padloc says 'Updated on Sep 9, 2022'.
  - correction: GitHub dates Padloc's last release, v4.3.0, to 2023-03-06; its feed entry was last updated on 2023-04-28. The Android app on Google Play has not been updated since 2022-09-09. Either way the project is stale.
- [corrected] (claim 4) Issue 6: a malicious server can swap encrypted fields.
  - evidence: Issue 6 is titled 'Icon URL Item Decryption (Medium)': 'due to insufficient key separation, a malicious server could swap encrypted field contents within items. By placing a sensitive field's ciphertext (such as a password) in the URL field position, the client would decrypt it as a URL and potentially leak the plaintext through the icon fetch request.' It requires 'items without per-item keys (created before July 2024)'. Status: 'Resolved post-assessment'. Field swapping as such is the paper's attack BW05: 'Nothing binds a ciphertext to a particular item field.'
  - correction: Issue 6 is a Medium-rated leak of a field's plaintext through the icon request. Field swapping is how the attack works, not the issue itself. Bitwarden says it is resolved for items with per-item keys (created after July 2024). The general finding that ciphertexts are not bound to their field is the paper's BW05.
- [unverifiable] (claim 7) Recurity Labs rated data left in SQLite and write-ahead-log files after sign-out as Medium.
  - evidence: Proton's blog post does not mention this finding or its rating. It names only memory-handling observations. The report itself is an end-to-end encrypted Proton Drive share (drive.proton.me/urls/T9BGC6B11W, linked from the blog) that has to be decrypted on the client. My attempt to retrieve it was blocked by the permission system, so I did not read it. Only secondary sources state the rating: cyberinsider.com (2026-05-13) calls it medium-severity and says it concerns Android sign-out with 'remove data' selected. Recurity's own site does not publish the report.
- [corrected] (claim 11) Self-hosting Vaultwarden requires an always-on machine.
  - evidence: Neither Vaultwarden nor Bitwarden documentation says this. bitwarden.com/help/using-bitwarden-offline: apps keep working offline 'in read-only mode', but edits and additions need the server.
  - correction: The server must be reachable whenever the user adds, edits or syncs items. Reading works offline (on mobile, up to the 90-day session limit). An always-on machine is the practical consequence, not a documented requirement.
- [corrected] (claim 11) Self-hosting Vaultwarden requires Docker.
  - evidence: Vaultwarden README: 'The recommended way to install and use Vaultwarden is via our container images'. It allows replacing docker with podman, and mentions 'community driven packages' and the option to 'build Vaultwarden yourself'.
  - correction: Containers (Docker or Podman) are recommended but not required.
- [corrected] (claim 11) Self-hosting needs a domain with HTTPS because the Bitwarden Android app forbids cleartext traffic.
  - evidence: $BW/app/src/main/res/xml/network_security_config.xml:4 has <base-config cleartextTrafficPermitted="false">, and AndroidManifest.xml:44 points to that config. The Vaultwarden README says 'The web-vault requires the use of HTTPS'. But lines 8-11 of the same config add <certificates src="user"/> ('Additionally trust user added CAs') for every non-Bitwarden domain.
  - correction: HTTPS is required. A public domain is not: because the app trusts user-installed CAs, a certificate from a private CA on a LAN hostname or IP also works. A domain with Let's Encrypt is simply the easiest route.

## Missed issues
- The report calls the file-less credential-exchange library alpha, and that is out of date. Google Maven lists androidx.credentials.providerevents up to 1.0.0-beta01 (maven-metadata <release>1.0.0-beta01, lastUpdated 20260909170339; POM Last-Modified 9 Sep 2026). Bitwarden still pins 1.0.0-alpha06 ($BW/gradle/libs.versions.toml:24). Update 'Not settled' item 2.
- The Google Password Manager advice leaves out Google's stated plan. support.google.com/accounts/answer/11350823 says on-device encryption 'can't be removed. Over time, this security measure will be set up for everyone'. It also says a user who loses every recovery option loses all passwords, and the only way out (passwords.google.com/encryption/reset → Turn off) deletes them all. 'Default is not zero-knowledge' is true today but changing, and the irreversibility will soon affect ordinary users. Warn the user.
- Google's own help pages give different Android export labels. 13068232 says 'Settings > Export passwords & passkeys > Download file'. 95606 (Android) says 'Tap Settings > Export passwords' and skips 'Autofill and passwords'. User instructions should not depend on one exact label. Google's 'delete your .csv file' warning appears under Import (Step 3), not under Export.
- Proton's own pages contradict 'Proton Pass offline reading not verified'. proton.me/pass/download/android says 'Offline access: Always access your passwords and other important information, even without an internet connection'. The Play listing the author saved (web/play/proton.android.pass.txt) says 'OFFLINE ACCESS ... even without an internet connection'. The desktop support page says only 'Paid users can even access the app offline'. Report what the vendor claims and mark it as unverified.
- The Proton Pass free tier also limits two-factor codes: 'Up to three 2FA items' (support/proton-pass-plans-explained). The 2 vaults figure is correct, but cite support/proton-plans for it. /pass/pricing renders a '0 vaults' placeholder in its HTML.
- The ETH mapping in Finding 6 is imprecise. Bitwarden's 'Issue 6' is Icon URL Item Decryption: Medium, resolved for items with per-item keys (created after July 2024). Field swapping is the paper's BW05: 'Nothing binds a ciphertext to a particular item field ... an adversary can swap around ciphertexts from different fields within an item.' The paper presents 12 attacks on Bitwarden; Bitwarden's summary groups them into 10. Cite BW04/BW05 when justifying our authenticated-data and record-id binding.
- The count of 'nine third-party security reports for 2025' overstates the assurance for Android. Six of the nine are Cure53 audits of the browser extension, core, desktop, RustCrypto and web vault. One is academic (ETH). Only one (Unit 42) covers the mobile apps. Also, Cure53's 2024 biometric bypass BWN-11-005 was only 'partially fixed post-assessment' according to Bitwarden's own summary. Later audits (Mandiant, Unit 42) raised no biometric issue, and Unit 42 lists biometric and Keystore handling under 'Effective Controls'.
- Keyguard is not paid-only. keyguard.dev/docs/premium says only Google Play builds lock features; the GitHub APK and the F-Droid custom-repository builds have 'everything unlocked'. Section 6's 'paid editing (Keyguard)' is true only for the Play build. Tell the user that sideloading is the free route, and that KeePass support is beta and 'not yet fully compatible with standard KeePass clients'.
- Padloc is staler than the report says. GitHub dates v4.3.0 (the latest) to 2023-03-06, with assets built that day. The Play listing app.padloc was last updated on 2022-09-09.
- Self-hosting requirements are overstated in two places, though the conclusion holds. The Vaultwarden README recommends containers but does not require Docker. The Bitwarden Android network_security_config (lines 8-11) trusts user-installed CAs, so HTTPS is mandatory but a public domain is not. The server also needs to be reachable only to edit or sync, because reading works offline.
- Licence detail matters if anyone copies SDK code. Bitwarden's SDK crates are 'GPL-3.0-only OR LicenseRef-Bitwarden-SDK' (crates/bitwarden-uniffi/Cargo.toml:12). Everything under bitwarden_license/ is SDK-licence-only. SDK License v2.0 (7 Oct 2025) clause 1.3 limits use to apps that interoperate with Bitwarden servers. For our local-only app the GPL-3.0-only route is the only option. Passbolt is AGPL version 3 only, with a trademark exception under section 7(e).
- The 'Lessons' bullet on SQLite and write-ahead-log leftovers cites a 'Medium' rating found only in a secondary source (cyberinsider). Proton's own announcement of 2026-05-12 does not mention it, and the primary report sits in an encrypted Proton Drive share that I could not open. The engineering lesson (delete -wal and -shm files on erase) stands without the rating, so drop the severity or mark it as secondary.
- Section 6 never weighs 2FAS Pass, the closest existing match to the user's no-account request. 2fas.com/pass/pricing: 'No user accounts required', Free tier 'Item Limit: Up to 200', Unlimited at '$9.99 / year'. Its BUSL licence matters for copying code, not for using the app. offline.md covers it, but this report's 'The rest do not suit this user' list skips it.
