# Verification: account-based (code lens) — independent check, 2026-10-06

## Overall
Within the code-and-artifact lens the report is mostly accurate. Almost every Bitwarden, Proton and Chromium citation matches the cited lines in today's trees, the shipped Bitwarden SDK agrees with the HEAD files it used, and the PIN envelope's AEAD really is AES-256-GCM. Before we rely on it, fix four things. Proton's 3 wrong PINs fall back to the account password and do not sign the user out. Bitwarden's 'field-by-field, no associated data' needs the qualifier that V2 accounts already get sealed AES-256-GCM blobs. Proton's 'clear only if unchanged' clipboard check cannot read the clipboard from the background on API 29+, so it is not a technique to copy as described. allowBackup="false" is ignored for device-to-device transfer on every app targeting API 31+, not only on some devices.

## Not confirmed
- [corrected] (claim 1) There is no account-less mode; the app offers only bitwarden.com, bitwarden.eu, a government region or a self-hosted URL (Environment.kt).
  - evidence: $BW/data/src/main/kotlin/com/bitwarden/data/repository/model/Environment.kt:84-89 defines the types US, EU, FED_RAMP and SELF_HOSTED. However, LandingViewModel.kt:345-349 removes FED_RAMP from the options unless remote flag FlagKey.FedRamp ('fedramp-gov-region') is on, and that flag defaults to false (core/.../FlagKey.kt:174-177). LandingViewModel.kt:354 also blocks account creation for FedRAMP. RootNavViewModel.kt:89-96 sends any state without a logged-in account to the Auth screens.
  - correction: No account-less or server-less mode exists. A user can pick bitwarden.com, bitwarden.eu or a self-hosted URL. The bitwarden-gov.com region is in the code but stays hidden behind a remote flag that is off by default.
- [corrected] (claim 6) Its permissions are INTERNET, ACCESS_NETWORK_STATE, ACCESS_LOCAL_NETWORK, USE_BIOMETRIC, NFC, CAMERA, a headset camera permission, POST_NOTIFICATIONS and READ_USER_DICTIONARY.
  - evidence: app/src/main/AndroidManifest.xml:12-20 declares exactly those nine. ACCESS_LOCAL_NETWORK exists in android-37 api-versions.xml since 37.0. The shipped APK's merged manifest is larger. The work-runtime-2.11.2.aar manifest, downloaded from Google Maven today and used at app/build.gradle.kts:276, adds WAKE_LOCK, ACCESS_NETWORK_STATE, RECEIVE_BOOT_COMPLETED and FOREGROUND_SERVICE. billing-9.1.0.aar (standardImplementation, line 295) adds com.android.vending.BILLING. Lines 28-33 also define a signature|knownSigner AUTHENTICATOR_BRIDGE_SERVICE permission. I did not check the Firebase AARs.
  - correction: Those nine are what the app module's own manifest declares. The installed Play build also requests at least WAKE_LOCK, RECEIVE_BOOT_COMPLETED, FOREGROUND_SERVICE and com.android.vending.BILLING, which come from libraries.
- [corrected] (claim 8) Bitwarden encrypts each item field separately with AES-256-CBC plus HMAC-SHA256 ('2.iv|ciphertext|mac') with no associated data.
  - evidence: hazmat/symmetric_encryption/aes256_cbc_hmac_sha256_ae.rs:1-4 says it 'has no support for associated data (it is not AEAD)', and 86-98 computes the MAC over iv‖ciphertext. enc_string/symmetric.rs:311-329 serialises the format as '2.' + base64(iv)|base64(data)|base64(mac). Per-item keys are always AES-CBC-HMAC (store/context.rs:517-519; cipher.rs:936-949). However, CiphersClient::encrypt seals personal items as a single blob when the account's signed security state is >= 2 (bitwarden-vault/src/cipher/cipher_client/mod.rs:42-47, 104-108; same logic at the shipped @20e5595c, lines 111-114). BLOB_SECURITY_VERSION = 2 (security_state.rs:36), and SecurityState::new() gives V2 accounts version 2 (68-70). blob/encryption.rs:89-147 puts name, notes, login, card, fields and password history into Cipher.data, sealed by DataEnvelope with AES-256-GCM (safe/data_envelope.rs:150) under a fresh content key wrapped by the item key. Android reaches this path through VaultSdkSourceImpl.kt:318-327 and bitwarden-uniffi/src/vault/ciphers.rs:16-17. The cipher README's 'all encryption entry points go through the legacy field-level path' is out of date relative to this code.
  - correction: Field-by-field type-2 encryption without associated data applies to V1 accounts and to organisation items; Android registrations are V1 unless the V2 flag is on. For V2 accounts, the shipped SDK already seals personal items as one AES-256-GCM blob.
- [corrected] (claim 9) Proton Pass signs users out after 3 wrong PINs.
  - evidence: EnterPinViewModel.kt:125-147: after 3 wrong PINs (MAX_PIN_ATTEMPTS = 3, PinConstants.kt:22), the result depends on the origin. From AUTO_LOCK, the normal unlock (UnAuthGraph.kt:95-98), it emits ForcePassword: the PIN sheet closes (EnterPinBottomsheet.kt:52) and PIN and biometrics are hidden because pinAttemptsCount >= 3 (AuthViewModel.kt:205-206, 504-508), leaving the Proton account-password form. Only from CONFIGURE_PIN_OR_BIOMETRY, i.e. re-entering the PIN in settings (AppGraph.kt:960-963), does it emit ForceSignOutAllUsers (MainActivity.kt:221 calls launcherViewModel.disableAll()). After that, 3 wrong account passwords trigger ForceSignOut (AuthViewModel.kt:434-458, 618-621 MAX_WRONG_PASSWORD_ATTEMPTS = 3).
  - correction: At the normal lock screen, 3 wrong PINs remove the PIN and biometric options and require the Proton account password; 3 wrong passwords then sign that user out. Only 3 wrong PINs entered while changing lock settings sign out all users.
- [corrected] (claim 10) Clipboard: Proton sets the sensitive flag.
  - evidence: $PP/clipboard/api/.../ClipboardManager.kt:25 declares copyToClipboard(text, isSecure: Boolean = false). ClipboardManagerImpl applies EXTRA_IS_SENSITIVE (literal key below API 33) only when isSecure is true. Callers set it for passwords, card numbers, CVVs and generated passwords (HomeViewModel.kt:967-998, ItemOptionsViewModel.kt:118, GeneratePasswordViewModel.kt:180). Usernames, emails, notes and TOTP codes are copied without the flag.
  - correction: Proton marks only secret fields as sensitive. Every copy, flagged or not, is still scheduled for clearing.

## Missed issues
- Finding 4 and the comparison text misstate Proton Pass: 3 wrong PINs at the normal lock screen fall back to the account password and do not sign anyone out. Sign-out happens after 3 wrong PINs entered from settings (all users) or 3 wrong account passwords. Evidence: EnterPinViewModel.kt:125-147, AuthViewModel.kt:205-206, 434-458, 618-621, AppGraph.kt:960-963. The 'do not wipe' advice still stands on Bitwarden's evidence alone.
- Finding 6 and section 2 understate how Bitwarden encrypts items today. The SDK shipped in Android 2026.9.1 (sdk-internal@20e5595c) already seals personal items of V2 accounts (security state >= 2) as one AES-256-GCM DataEnvelope blob, with only metadata left in plaintext. Evidence: cipher_client/mod.rs:42-47, 104-108; security_state.rs:36; blob/encryption.rs:89-147; data_envelope.rs:150. The report's 'preparing sealed blobs' came from a README that is out of date relative to the code. Field-by-field type 2 still applies to V1 accounts, which includes every Android registration while flag pm-27278 stays off, and to organisation items.
- The lesson 'copy Proton's clipboard check (clear only if our value is still there)' does not work as described on API 29+. In AOSP android17-release ClipboardService.java, reads need window focus (1392-1403), hasPrimaryClip returns false without it (742-757), and writes are allowed without focus (1429-1431). Proton's receiver runs in the background, so it almost always takes the 'cannot read → clear' branch and clears unconditionally. The check only helps on API 24-28 or while our app is in the foreground. clearPrimaryClip is API 28+, so API 24-27 need setPrimaryClip(ClipData.newPlainText("", "")), as Proton does at ClipboardManagerImpl.
- allowBackup="false" fails to stop device-to-device transfer on every device, not just 'some devices', once an app targets API 31+. AOSP android17-release BackupEligibilityRules.java:115-122 and 254-267: IGNORE_ALLOW_BACKUP_IN_D2D (@EnabledSince S) forces D2D eligibility for all non-system apps. Our targetSdk-37 app must therefore exclude data in <device-transfer> of data_extraction_rules. Proton Pass (targetSdk 36, allowBackup only) is D2D-eligible, including its unencrypted Room metadata.
- Libraries bring permissions. The work-runtime-2.11.2 AAR manifest adds WAKE_LOCK, ACCESS_NETWORK_STATE, RECEIVE_BOOT_COMPLETED and FOREGROUND_SERVICE. Copying Bitwarden's WorkManager clipboard-clear would add these to a local-only app unless we remove them with tools:node="remove" or use AlarmManager instead. Bitwarden's listed permissions come from its source manifest only.
- Proton does not set FLAG_SECURE 'on every activity'. setSecureMode is called only in MainActivity, EnterExtraPasswordActivity, AutofillActivity and AutosaveActivity. The Credential Manager Password/Passkey Selection, Creation and Usage activities, ShortcutActivity and InlineSuggestionsNoUiActivity never call it (grep in $PP/features/credentials and app/). For our app, apply FLAG_SECURE to every activity that shows vault data.
- One open item is now resolved: Proton core 36.8.0, the version Pass pins, has a crypto-android AndroidKeyStoreCrypto.kt byte-identical to the HEAD copy (sha256 a869c22b...). Its bytecode confirms the pass-through when no Keystore key is available. EncryptionContextProviderImpl.kt:139-145 would then write pass.key unencrypted. This supports finding 5.
- For the importer, Chromium's 'name' column is a Chrome-derived site or app display name (credential_ui_entry.cc:311-322), not a user-set title. The export writes one row per affiliated domain, so one credential can appear several times (password_csv_writer.cc:55-59), and rows are sorted (61-73). Chrome's own importer ignores 'name', trims header whitespace and rejects files with two columns mapping to the same label (csv_password_sequence.cc:51-55, 126-133).
- The statement that 'the library is alpha' is out of date. Google Maven metadata for androidx.credentials.providerevents:providerevents lists 1.0.0-beta01 (lastUpdated 2026-09-09); Bitwarden still pins 1.0.0-alpha06.
- The report cites HEAD trees. bitwarden/android HEAD pins sdk 4.0.0-9248-c815b283, while the released v2026.9.1-bwpm pins 3.0.0-8826-20e5595c. I compared the cited SDK files at the shipped commit. The envelope, COSE and AES-CBC-HMAC files are identical, kdf.rs differs only in wasm attributes, and enroll_pin and blob dispatch are present. The conclusions hold for the shipped app, but future citations should pin to the release tag.
- Bitwarden maps a missing stored timeout to Never (SettingsRepositoryImpl.kt:776-788), so its 15-minute default depends on login code writing it. Our app should store an explicit default and treat a missing value as the strictest setting, not as 'never lock'.
- Two more things the report could add to its lessons. Proton enables PRAGMA secure_delete = ON on its main database (AppDatabase.kt:346-356), which is relevant to 'avoid leftovers'. Jetpack EncryptedSharedPreferences and MasterKey carry @Deprecated in the androidx.security:security-crypto 1.1.0 classes.jar, which is a stronger reason for 'avoid EncryptedSharedPreferences' than Bitwarden having moved away from it.
- minSdk-24 API levels from android-37 api-versions.xml, for the lessons section. setInvalidatedByBiometricEnrollment is API 24. setIsStrongBoxBacked and StrongBoxUnavailableException are API 28, so key generation needs a non-StrongBox fallback. setUnlockedDeviceRequired is API 28. setUserAuthenticationParameters and AUTH_BIOMETRIC_STRONG are API 30; below that use the deprecated setUserAuthenticationValidityDurationSeconds(-1). ClipDescription.setExtras is API 24 and EXTRA_IS_SENSITIVE API 33 (the literal key works earlier). setRecentsScreenshotEnabled is API 33. An AES Keystore key without setKeySize is 128-bit (AOSP KeyGeneratorSpi:58, 185), so set 256 explicitly.
