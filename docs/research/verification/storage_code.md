# Verification: storage (code lens) — independent check, 2026-10-06

## Overall
Within the code and artifact lens, the report's library and app facts mostly hold. Claims 6-8 (Aegis, the app storage choices and Room versions) and the AtomicFile, Os, kotlinx and SQLCipher facts all check against today's artifacts, with smaller corrections: three SQLCipher raw-key shapes, the driver also works on Room 2.8.5, java.nio.file can be desugared, and openRead deletes .new only when the base file exists. What must change before we build: drop the DataStore endorsement (its API 26+ move is unlink-then-rename, not atomic), and harden section 5. That means no-overwrite generation allocation, no 'wrong password' until older generations' slots have been tried, retention that knows which files are valid and ignores the wall clock, no pruning or success report after a failed directory fsync, and data-key rotation on password change.

## Not confirmed
- [corrected] (claim 1) openRead deletes a stale .new file.
  - evidence: AtomicFile.java:174-178: `if (mNewName.exists() && mBaseName.exists()) { if (!mNewName.delete()) Log.e(...) }`, then `return new FileInputStream(mBaseName)`.
  - correction: openRead deletes the .new file only when the base file also exists. When only a .new file is present (the first-ever write was interrupted), openRead neither deletes nor uses it and throws FileNotFoundException.
- [corrected] (claim 3) FileStorage moves the temp file into place and throws on failure.
  - evidence: FileStorage.kt:113-125 throws IOException("Unable to rename …") when atomicMoveTo returns false, and deletes the scratch file before rethrowing. FileMoves.android.kt:26-44: below API 26 it uses `renameTo(toFile)`; on API 26+ it calls `Files.move(srcFile.toPath(), dstFile.toPath(), StandardCopyOption.REPLACE_EXISTING)` without ATOMIC_MOVE. Android libcore android17-release (LinuxFileSystemProvider extends UnixFileSystemProvider, move → UnixCopyFile.move, lines 441-479; same logic at android-8.0.0_r1) handles that by running `unlink(target)` and then `rename(source, target)`. FileReadScope.readData (FileStorage.kt:161-183) returns `serializer.defaultValue` when the file is missing.
  - correction: It throws on failure, but the move is atomic only below API 26. On API 26 and later it is unlink-then-rename. A kill or crash between the two calls leaves no file at the target path, and DataStore then silently returns the default (empty) value. DataStore 1.3.0-alpha11 changed this to `Files.move(source, destination, ATOMIC_MOVE, REPLACE_EXISTING)` with a fallback.
- [corrected] (claim 4) java.nio.file.Files is unavailable below API 26 (the report says 'unusable at minSdk 24').
  - evidence: api-versions.xml: `java/nio/file/Files since="26"`, `java/nio/file/StandardCopyOption since="26"`, `java/io/File.toPath since="26"`. Google Maven also has com.android.tools:desugar_jdk_libs_nio:2.1.5: its jar contains java/nio/file/Files.class and sun/nio/fs/UnixCopyFile.class, and its configuration rewrites java.nio.file.* to j$.nio.file.* for api_level_below_or_equal 25.
  - correction: The platform lacks java.nio.file below API 26, but core library desugaring with desugar_jdk_libs_nio makes it usable at minSdk 24. The design choice still holds: Os.rename is better, because Files.move without ATOMIC_MOVE is not atomic.
- [corrected] (claim 5) The driver is 'the Room 3 path' (and SupportOpenHelperFactory is for Room 2).
  - evidence: javap of room3-runtime-android-3.0.3: RoomDatabase$Builder has setDriver(androidx.sqlite.SQLiteDriver) and no openHelperFactory, and the room3 classes contain no androidx/sqlite/db/SupportSQLite references. javap of room-runtime-android-2.8.5 (sha1 = Google Maven) shows both `openHelperFactory(androidx.sqlite.db.SupportSQLiteOpenHelper$Factory)` and `setDriver(androidx.sqlite.SQLiteDriver)`.
  - correction: Room 3 accepts only drivers, but Room 2.8.5 (Room 2.7 and later) also accepts an SQLiteDriver through setDriver. SQLCipherDriver is therefore not limited to Room 3; the only Room-2-only path is SupportOpenHelperFactory.
- [corrected] (claim 5) Unless the key has the form x'<64 hex digits>', SQLCipher derives it with PBKDF2-HMAC-SHA512 at 256,000 iterations.
  - evidence: libsqlcipher.so strings show the AAR bundles SQLCipher core "4.19.0" "community" (SQLite 3.53.4). sqlcipher.c at v4.19.0: :111 `#define PBKDF2_ITER 256000`, :297 `default_kdf_iter = PBKDF2_ITER`, :301 `default_kdf_algorithm = SQLCIPHER_PBKDF2_HMAC_SHA512`. :1881-1907 checks blob_format (`sqlite3StrNICmp(pass,"x'",2)`, trailing `'`, hex) and accepts pass_sz == raw_key_sz+3, raw_key_sz+raw_salt_sz+3, or 2*raw_key_sz+raw_salt_sz+3; any other input goes to PBKDF2.
  - correction: Three raw-key forms skip PBKDF2: x'<64 hex>' (key only), x'<96 hex>' (key plus 16-byte salt) and x'<160 hex>' (key, HMAC key and salt). The x' prefix is case-insensitive. Any other input gets PBKDF2-HMAC-SHA512 × 256,000 by default, changeable by PRAGMA. The report's 67-byte x'<64 hex>' form is correct.
- [corrected] (claim 9) 'The target name never exists beforehand, so no good file is ever replaced.'
  - evidence: Os.rename is rename(2), whose man page (saved rename2.txt:38) says "If newpath already exists, it will be atomically replaced". The sketch never checks dst.exists(), and the spec never says how gen is chosen. If gen = loaded generation + 1 after a fall-back open (newest file damaged), the save silently replaces the damaged file, which breaks 'never delete a file that failed'. With a password-aware fallback it could replace a newer, intact file.
  - correction: The invariant has to be enforced. Allocate gen = 1 + the highest number among all names on disk, including .tmp, damaged, quarantined and unparseable ones. In commit(), check dst.exists() under the Mutex and throw before renaming.
- [corrected] (claim 9) If the directory fsync fails, the save can be treated as committed: log it, then publish the new state and prune.
  - evidence: In the sketch, `catch (e: ErrnoException) { /* committed; durability unconfirmed: log it */ }` is followed by 'publish the new state and prune'. A directory fsync failure means the ext4 journal commit or f2fs checkpoint did not complete (see the next item). After a reboot the new generation may be gone although the user was told it was saved. Os.open can also fail with EMFILE and take the same path.
  - correction: The files stay openable because of metadata ordering, but the save must not be reported as done. Do not prune on that save. Surface a 'storage error' state and prune only after a later directory fsync succeeds. Do not retry the same fsync and trust it: Linux reports a writeback error once.
- [refuted] (claim 9) An unkeyed SHA-256 trailer plus the AEAD tags separate 'file damaged' from 'wrong password' in every case.
  - evidence: Counterexamples drawn from the spec's own rules ('trailer passes but the data key will not unwrap: wrong password'; header = AAD): (a) If the slot or the KDF parameters are wrong before the trailer is computed (a bug, a password-encoding change like Aegis's afb9e59, a RAM bit flip), the trailer passes and the unwrap fails. The user is told 'wrong password' with the right password, and the rules stop instead of trying older generations. Verify-before-commit catches this only if it re-derives the key from the password and unwraps the written slot; a payload check with the cached data key passes, because the bad header was already the AAD at sealing time. (b) After a password change, if the newer generations are damaged, the newest trailer-valid file was sealed under the old password, so the current password is reported 'wrong'. (c) Damage confined to the 32-byte trailer throws away an intact newest file whose GCM tag would verify. (d) If major or headerLen are read before the trailer is checked, one flipped bit gives a false 'newer version' refusal or an allocation of up to 4 GiB.
  - correction: The trailer separates damage that happened after the write from a wrong password. It cannot catch bad bytes produced before sealing, or generations sealed under different passwords. Report 'wrong password' only when no retained generation's slot opens with the typed password. Let a verified AEAD take precedence over a failed trailer. Check the trailer before trusting any header field. Never offer a destructive 'reset vault' in response to 'wrong password', because a non-expert would take it.
- [refuted] (claim 9) The pruning rule (keep the 5 newest plus the newest of each of the last 14 days) cannot delete the only good copy.
  - evidence: Simulation /tmp/claude-1000/-home-asus-AndroidStudioProjects-PasswordVault/096e95f8-3ae0-41bf-b235-08771bb88852/scratchpad/verify-storage-code/test/prune_sim.py, applying the exact rule after each save. (A) New install, 7 saves on day 1, saves 3-7 bad: keeps [3..7] and no good copy. (B) 20 good daily saves, the device clock jumps forward 30 days, then 5 bad saves: keeps [21..25] and no good copy. (C) A bug that persists for 15 days at one save a day: keeps gens 5-18 and no good copy. 'Bad' means anything the in-memory verify cannot see, such as a semantic or slot bug (see the previous item). The rule also counts damaged files toward the 5 and later prunes them, which contradicts 'never delete a file that failed'. Its day buckets also depend on the wall clock.
  - correction: Make retention aware of validity and independent of the clock. Never prune below the newest N generations that a later app start has opened successfully from disk. Move failed files to a quarantine name that pruning ignores; GCM ciphertext can still be decrypted in CTR mode to salvage entries. Key retention to generation numbers or monotonic counters, not wall-clock days. Pin the last generation of each app version and of each password epoch.

## Missed issues
- DataStore 1.2.1 does not replace its file atomically on API 26 and later, so the report's verdict that it is 'the better ready-made writer' (5.3) and its table cell 'temp, fsync, move, throws on failure' are unsupported. FileMoves.android.kt:34-44 calls Files.move(src, dst, REPLACE_EXISTING) without ATOMIC_MOVE. Android's default provider (LinuxFileSystemProvider extends UnixFileSystemProvider, which calls UnixCopyFile.move, android17-release lines 441-479, same at android-8.0.0_r1) runs unlink(target) and then rename(). A kill or crash between them leaves only the .tmp file, and FileReadScope.readData (FileStorage.kt:161-183) then silently returns serializer.defaultValue. DataStore 1.3.0-alpha11 now tries ATOMIC_MOVE first. Rule for our code: never call Files.move without ATOMIC_MOVE; Os.rename is the right primitive.
- Generations plus one long-lived data key. The spec wraps a single random data key with the password-derived key and keeps up to 19 older generations. After a master-password change (say, because the old one leaked), every older generation still has a slot that the OLD password opens. The data key it yields decrypts every newer generation too, unless the data key is rotated and the payload re-encrypted on password change. The report's own remedy in 'Not settled' (re-wrap or delete older generations) conflicts with its rule never to replace a file. It would also delete every fallback at the moment the new slot is least tested.
- The benchmark (storage/bench/VaultBench.java) does not exercise the specified procedure. It overwrites one name with Files.move(ATOMIC_MOVE, REPLACE_EXISTING) instead of writing new generation names. It omits Argon2, the SHA-256 trailer, the in-memory re-open and compare, and pruning. It ran on desktop NVMe ext4, where a directory fsync is one journal commit. On f2fs every directory fsync forces a full checkpoint (f2fs_do_sync_file → need_do_checkpoint returns CP_NON_REGULAR → f2fs_sync_fs), so per-save latency on a phone has not been measured; the report's 'ten times slower' is only an inference. Its corruption test checks the GCM tag only, not the trailer-based damaged-versus-wrong-password classification.
- Export should copy the generation that was opened and verified in this session, not 'the newest generation'. Under the spec's own fallback rules the newest file may be the damaged one, or one sealed under a different password.
- Partial update to 'Not settled': the kernel sources show both Android /data filesystems implement directory fsync (ext4_force_commit on ext4, a full checkpoint on f2fs, in android15-6.6 and android16-6.12). What remains to test on a device is only opening the app's own filesDir subdirectory with O_RDONLY on API 24 and 37, plus the cost of an f2fs checkpoint per save.
