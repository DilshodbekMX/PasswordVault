# Verification: crypto (code lens) — independent check, 2026-10-06

## Overall
Within the code-and-artifact lens the report is mostly accurate. Every version, date, licence, ABI list, 16 KB alignment result and Maven fact I checked holds, both Argon2id vectors reproduce from BC 1.86 and from the PHC C code that argon2kt bundles, and the Aegis, Bitwarden, Proton and Conscrypt citations match the source. Before we build on it, fix these: argon2kt's buffer handling (what is leaked or wiped, and that it hashes the buffer's capacity), the claim that Keystore keys require authentication by default, Destroyable on API 24–25, and the misstated Bitwarden and KeePassDX bound-first examples. In the design: the change-password flow can lose the vault, the AAD definitions conflict, the reader accepts zero password slots, the biometric slot is removed on transient Keystore errors (containsAlias or a plain InvalidKeyException), and the Compose undo history keeps the password.

## Not confirmed
- [corrected] (claim 1) hash() returns direct ByteBuffers for the raw hash and the encoded output, and the library never zeroes or frees them.
  - evidence: v1.6.0 lib/src/main/cpp/jni/Argon2Jni.cpp:43-45 and 56-58 malloc both outputs and wrap them with NewDirectByteBuffer. No free() exists anywhere, so both allocations leak, and they also leak on the error return at lines 72-74. Argon2Jni.kt:64-67 returns encodedOutput = encodedTarget.dropLastN(1). ByteBufferTarget.kt:47 copies it into a new ByteBuffer.allocateDirect buffer, and line 55 overwrites the original native buffer with java.util.Random bytes (Argon2KtUtils.kt:54-61). Separately, argon2_hash zeroes its own work memory (core.c:148 FLAG_clear_internal_memory = 1).
  - correction: rawHash wraps malloc'd native memory that is never zeroed or freed. encodedOutput is a JVM allocateDirect copy that the GC reclaims but nobody zeroes. The original native encoded buffer is overwritten with random bytes and then leaked. The caller must overwrite both returned buffers, and must avoid rawHashAsByteArray() and encodedOutputAsString() (Argon2Kt.kt:213 and 222), which make heap copies.
- [corrected] (claim 4) Aegis exports and Android backups reuse the master key (VaultRepository.java around line 168).
  - evidence: vault/VaultRepository.java:166-169 runs creds = creds.exportable(), and VaultFileCredentials.java:48-50 returns new VaultFileCredentials(_key, _slots.exportable()), i.e. the same key. Automatic backups use VaultManager.java:175 _repo.export(outStream). Android backups go through AegisBackupAgent.java:78-79 vaultFile.exportable().toBytes(), which per VaultFile.java:124-133 is the same ciphertext and key with filtered slots. Only an encrypted export of an unencrypted vault creates a new key (ImportExportPreferencesFragment.java:457).
  - correction: True. VaultRepository.java:168 is the export and automatic-backup path. The Android cloud-backup path is AegisBackupAgent.java:78-79 together with VaultFile.exportable() (VaultFile.java:124-133).
- [corrected] (claim 5) AOSP KeyGenParameterSpec.Builder (android17-release) defaults to requiring authentication for every use.
  - evidence: android17-release keystore/java/android/security/keystore/KeyGenParameterSpec.java:1029 declares 'private boolean mUserAuthenticationRequired;' (false), and the javadoc at :1477 says 'By default, the key is authorized to be used regardless of whether the user has been authenticated.' :1030 sets mUserAuthenticationValidityDurationSeconds = 0. KeyStore2ParameterUtils.java:311-324 adds KM_TAG_NO_AUTH_REQUIRED when auth is not required; when it is required and the timeout is 0, no AUTH_TIMEOUT is set, which means every use is authenticated. The report's lines 964-978 are AOSP main's numbering; in android17-release the block is at 1028-1046.
  - correction: By default the key needs no user authentication. Once setUserAuthenticationRequired(true) is called, the defaults make it per-use (timeout 0) and AUTH_BIOMETRIC_STRONG. The report's builder code calls it, so the design is unaffected, but the sentence and the line citation should be fixed.
- [corrected] (claim 7) TextFieldState has clearText().
  - evidence: TextFieldState.kt:778-783 defines the extension 'fun TextFieldState.clearText() { edit { delete(0, length); placeCursorAtEnd() } }'. :265-273 says 'programmatic edits contribute to undo history without merging'. TextUndoManager.kt:226-238 records preText = pre.substring(preRange), which here is the whole password, and :250 sets capacity 100. TextFieldKeyEventHandler.kt:263 calls textFieldState.undo() on the keyboard shortcut.
  - correction: clearText() exists as an extension function, but it pushes the full password into the undo stack, where Ctrl+Z can restore it. Call state.undoState.clearHistory() (ExperimentalFoundationApi) after clearText(), or drop the TextFieldState.
- [corrected] (claim 8) SecretKeySpec.destroy() throws DestroyFailedException by default.
  - evidence: libcore android17-release Destroyable.java:58-59 has 'public default void destroy() … { throw new DestroyFailedException(); }', and oreo-release is the same. The same file's :48-51 note says 'Up to and including API 25 this method did not have a default implementation'. nougat-mr1-release Destroyable.java:51 declares the abstract 'void destroy() throws DestroyFailedException;'. SecretKeySpec implements neither destroy nor isDestroyed (android.jar API 37 javap; nougat source).
  - correction: From API 26 on, destroy() throws DestroyFailedException. On API 24–25, which our minSdk 24 includes, calling destroy() on a SecretKeySpec throws AbstractMethodError, an Error that a DestroyFailedException catch does not stop. Never call it.
- [corrected] (claim 9) kdf.rs rejects weak parameters (InsufficientKdfParameters).
  - evidence: crates/bitwarden-crypto/src/keys/kdf.rs:12-16 sets PBKDF2_MIN_ITERATIONS 5000, ARGON2ID_MIN_MEMORY 16*1024 KiB, MIN_ITERATIONS 2, MIN_PARALLELISM 1, and :37-63 returns InsufficientKdfParameters below them in derive_kdf_key, the account master-key path. There is no maximum. The envelope's unseal path (:199-203, :488-500, :577-593) feeds file values straight to argon2::Params::new and applies neither the minimums nor any maximum.
  - correction: kdf.rs sets a floor only, and only for the account KDF. Bitwarden does not cap KDF cost before running it, so it is no precedent for the report's 'bound them first' upper limits.
- [corrected] (claim 10) KeePassDX refuses an Argon2 memory setting above three quarters of available memory.
  - evidence: The rule exists: kdf/Limits.kt:48-53 has KDF(maxMemory = UInt.MAX, 3f/4), AppUtil.kt:222-235 and 264-272 use availMem × ratio, and Argon2Kdf.kt:55-64 throws KDFMemoryDatabaseException. On open it does not reach the file's parameters. LoadDatabaseRunnable.kt:59 calls clearAndClose (Database.kt:941-947 nulls both databases), then Database.kt:560 runs kdfEngine?.checkLimits(limits) while kdfEngine (:339-340) is still null, before the file is read. mergeData does the same on a freshly created Database() (:636-638). While opening, KDBX parameters only pass Argon2Kdf.getValidatedParameters (:106-120): memory ≤ UInt.MAX (4 GiB), iterations ≤ UInt.MAX, parallelism ≤ 2^24−1 (:248-259). Native failures are mapped only afterwards (DatabaseInputKDBX.kt:227-232).
  - correction: KeePassDX caps the memory a user can set or save at 3/4 of availMem. A file being opened can demand up to 4 GiB before anything refuses it.
- [corrected] (claim 11) Design attack: is there a nonce-reuse path? (The §1 table also says every nonce, including wrap nonces, comes from SecureRandom().)
  - evidence: crypto.md §11: every KEK comes from a fresh salt (create, change password, constants upgrade, export) and wraps exactly once. Each body save uses a fresh random 96-bit nonce, far inside SP 800-38D's 2^32 budget. The Keystore wrap's IV is generated by Keystore. Conscrypt also refuses an encrypt re-init with the same key and IV (OpenSSLAeadCipher.java:188-194). The §1 table conflicts with §7 and §11: a caller IV on the biometric key fails with 'Caller-provided IV not permitted' (KeyStoreCryptoOperationUtils.java:141-142).
  - correction: There is no nonce-reuse path. Fix the §1 table: the biometric wrap's nonce must come from cipher.iv after init(ENCRYPT_MODE, key). Only software-key wraps and the body may use SecureRandom nonces.
- [corrected] (claim 11) Design attack: is the body AAD defined unambiguously?
  - evidence: crypto.md §1 table: 'The body's associated data (AAD) is every stored byte before the body nonce.' The layout block instead says 'body_ct AES-256-GCM(VK, body_nonce, body_json, AAD = all bytes above)', and 'all bytes above' includes body_nonce. The two definitions produce different AAD.
  - correction: This is a real specification bug. It is not exploitable, but it breaks interoperability with the published decrypt script and with other implementations. State once: AAD = magic ‖ header_len ‖ header (bytes 0 to 12+header_len, excluding the nonce). Ship a whole-file test vector.
- [corrected] (claim 11) Design attack: are there unauthenticated fields, parse ambiguities or gaps in the reader rules?
  - evidence: The length prefix, magic and header are all inside the AAD, and the KDF parameters, salt and version are hashed into H0 (RFC 9106 Figure 1, lines 245-248), so tampering is detected and no ambiguity between header and body survives authentication. Gaps remain in the §1 reader rules: they reject only 'more than one slot per type', so a file with zero password slots (biometric only) is accepted; argon2_version is not in the reject list, and argon2kt and BC both accept 0x10; duplicate or unknown JSON keys, trailing bytes and file size are unspecified.
  - correction: Require exactly one password slot and at most one biometric slot. Reject argon2_version ≠ 19, duplicate keys, unknown keys and trailing data. Bound the total file size: Conscrypt buffers the whole ciphertext until doFinal, so an oversized import means an OOM. The zero-password-slot gap is the one that could cost a vault: a writer bug would only show up when the Keystore key dies.
- [corrected] (claim 11) Design attack: do the reader bounds close resource exhaustion?
  - evidence: Reader bounds allow m up to 262,144 KiB, t up to 10 and p up to 8, and run before authentication. The BC fallback needs about 80 MB of Java heap for m = 64 MiB (measured: OOM at -Xmx76m, OK at -Xmx80m), so 256 MiB can never run on the fallback, and on low-RAM phones the native path risks being killed by the low-memory killer. The report's own §3 warns that calibrated memory can make a backup unopenable on a weaker phone.
  - correction: Partly a real problem. Either have version 1 require the exact constants (raises then come with a new version), or check capacity before running the KDF (BC: Runtime.maxMemory() minus used; native: ActivityManager.MemoryInfo or isLowRamDevice) and show a clear 'needs a stronger device' error instead of crashing.
- [corrected] (claim 11) Design attack: is there a downgrade or rollback path?
  - evidence: A cryptographic downgrade is closed: version, cipher and kdf are fixed and authenticated, and lowering the parameters changes the KEK. Rollback is not closed: any older generation, export or Android Auto Backup / device-to-device copy is accepted silently, and §11's 'Delete older generations, which the old password still opens' cannot reach backup-transport copies. The report never mentions allowBackup or dataExtractionRules. For comparison, Aegis sets allowBackup="true" with a backupAgent (AndroidManifest.xml:23-27).
  - correction: Low severity for a local threat model. Put a monotonically increasing generation counter in the authenticated header, compare it with the last value seen, and warn on rollback. Decide explicitly whether the vault file may enter Android backups; if it may, a password change cannot retire old ciphertext.
- [corrected] (claim 11) Design attack: can the create or change-password flows lose the vault?
  - evidence: §11 Change password: '(2) New VK … (3) Remove the biometric slot and its key. (4) Re-encrypt, write, read back. (5) Delete older generations'. The new password is never typed twice. The read-back can reuse the same in-memory bytes, so a typo or IME autocorrect is never caught. The same operation removes the only other way in (biometrics) and the generations that the old password opens, and step 3 deletes the Keystore key before step 4 commits the new file. Create and Export have no confirmation step either.
  - correction: This is a real loss path: one mistyped new password leaves no way into the vault. Fix: enter the new password twice. Read back from disk through the full unlock path, re-deriving the KEK from what the user retypes. Keep the previous generation until the first successful password unlock with the new password (or N days). Offer biometric re-enrolment of the new VK immediately, while the vault is still unlocked. Delete the old Keystore key only after the new file is committed. Apply 'type twice' to create and export as well.
- [corrected] (claim 11) Design attack: does the design match how the Android Keystore reports errors ('alias missing' and invalidation)?
  - evidence: android17-release AndroidKeyStoreSpi.java:158-163 implements engineContainsAlias as getKeyMetadata(alias) != null, and :164-179 returns null on any KeyStoreException (it only logs when the code is not KEY_NOT_FOUND). So containsAlias() returns false on transient Keystore failures. engineGetKey (:123-140) returns null only for KEY_NOT_FOUND. KeyStoreCryptoOperationUtils.java:126-127 turns every other Keystore error into a plain InvalidKeyException, the exception Aegis treats as invalidation (KeyStoreHandle.java:95-97). :117-120 also maps KEY_NOT_FOUND to KeyPermanentlyInvalidatedException, and :77-103 with :198-204 decides invalidation on the client side from BiometricManager.getAuthenticatorIds().
  - correction: This is a real mismatch. It costs only biometric unlock, never data, but it breaks the report's own rule 'anything else → use the password, change nothing'. Remove the slot only on KeyPermanentlyInvalidatedException from cipher.init, or when getKey() returns null. Treat containsAlias() == false and plain InvalidKeyException as transient: hide the option for this session and change nothing. Do not copy Aegis's plain-InvalidKeyException heuristic.

## Missed issues
- The examples in §2.5 do not support it. It says 'Bound them first, as Bitwarden (InsufficientKdfParameters, kdf.rs), KeePassDX (refuses above 3/4 of availMem) and age … do'. Bitwarden kdf.rs:12-16 and 37-63 set only minimums, on the account KDF, and the envelope's unseal path (password_protected_key_envelope.rs:199-203, 577-593) has no bound at all. KeePassDX's 3/4 check is a no-op when a file is opened (Database.kt:560 runs on a null kdfEngine after LoadDatabaseRunnable.kt:59 clearAndClose), so files may demand up to 4 GiB (Argon2Kdf.kt:248-259). Only age's spec text backs an upper bound. The recommendation is still right, but the precedents should be removed or corrected.
- argon2kt hashes the whole capacity of the password and salt buffers and ignores position and limit (Argon2Jni.cpp:33-34 and 38-39 GetDirectBufferCapacity). A direct buffer larger than the UTF-8 bytes silently gives a different key from Bouncy Castle. This is the same kind of bug as Aegis's afb9e59 migration (PasswordSlotDecryptTask.java:52-58; CryptoUtils.toBytesOld returns byteBuf.array()). Allocate exactly-sized direct buffers, pass the same byte[] to both implementations, and add non-ASCII and NFC-versus-NFD cases to the cross-check vectors. Also avoid Argon2KtResult.rawHashAsByteArray() and encodedOutputAsString(), which make heap copies of the KEK (Argon2Kt.kt:213 and 222).
- The §8 advice 'remember { TextFieldState() } … then clearText()' leaves the password reachable. clearText() is a programmatic edit that is recorded in the undo history (TextFieldState.kt:265-273), with the full deleted text kept as preText (TextUndoManager.kt:226-238, capacity 100 at :250), and the keyboard undo shortcut restores it (TextFieldKeyEventHandler.kt:263). Call undoState.clearHistory() or discard the state object. TextFieldState.Saver also saves the undo history (:670-679), one more reason to avoid rememberTextFieldState.
- minSdk 24 trap: on API 24–25, Destroyable.destroy() has no default (nougat-mr1-release Destroyable.java:51; android17 Destroyable.java:48-51 'Up to and including API 25 this method did not have a default implementation'), so SecretKeySpec.destroy() throws AbstractMethodError there, not DestroyFailedException. Conscrypt Cipher objects also keep their own raw-key copies (OpenSSLCipher.java:408-413 encodedKey; OpenSSLAeadCipher.java:196 previousKey), so drop Cipher references promptly.
- The 'Not settled' item on R8 can mostly be closed from the artifacts. argon2kt's JNI-reached members carry @Keep (javap: the Argon2Jni class and native methods, the ByteBufferTarget class and its byteBuffer field, which Argon2Jni.cpp:77-82 looks up by name). androidx.annotation's jar ships the rules that honour @Keep (annotation-jvm-1.10.0.jar META-INF/proguard/androidx-annotations.pro: '-keep @androidx.annotation.Keep class * {*;}'). Still run one minified build to confirm. Separately, the 1.6.0 natives were built with NDK r22 / clang 11.0.5 (strings in libargon2native.so) from the portable ref.c; the unreleased HEAD drops AppCompat.
- Issue #25's mitigation is unproven. The maintainer said 'There should be no difference between version 1.6.0 and 1.5.0', proposed a custom SoLoader, and closed the issue without the reporter confirming a fix. So the Bouncy Castle fallback is required, not optional, and loading must catch UnsatisfiedLinkError, which is an Error and not an Exception. The fallback in turn needs about 80 MB of Java heap at 64 MiB (measured), above the CDD minimum heap of 48 MB (hdpi) and at the 80 MB minimum (xhdpi) without largeHeap.
- java.util.Base64 exists only from API 26 (api-versions.xml: java/util/Base64 since="26"). With minSdk 24, the header's base64 fields need android.util.Base64 (since 8) or Kotlin's Base64.
- The KeyGenParameterSpec line numbers the report cites (964-978) come from AOSP main, not android17-release (1028-1046): the saved copy in crypto/web is byte-identical to main. The values are the same in both branches, but the citation does not match the branch the report names.
- Minor location error: Aegis's Android-backup reuse of the master key is in AegisBackupAgent.java:78-79 together with VaultFile.exportable() (VaultFile.java:124-133). VaultRepository.java:168 covers exports and the automatic SAF backups (VaultManager.java:175).
