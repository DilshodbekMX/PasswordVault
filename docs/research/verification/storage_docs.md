# Verification: storage (docs lens) — independent check, 2026-10-06

## Overall
For versions, dates, licences, documentation and standards, the report can mostly be trusted. Every Maven version and date in claim 1 checks out against Maven and the release notes today. So do the Room 3 facts, the security-crypto deprecation, the EncryptedFile overwrite refusal, the fsync(2), rename(2), f2fs and SQLite quotes, the SQLCipher licence and raw-key rules, Room's WAL default, KeePassXC's save guards and the KeePassDX zero-byte issues. Two things need fixing before we rely on the report. First, the 16 KB statement: Play already requires 16 KB support for a new app targeting 37. The guide now also has a RELRO test, which SQLCipher before 4.19.1 fails, as do argon2kt 1.6.0's 32-bit and x86_64 libraries. And B is not native-free once the crypto report's argon2kt is included. Second, the evidence against SQLCipher should be toned down: #81 and #89 are fixed and only affected minSdk 23, and #85 was the reporter's own misconfiguration. Pixels' fsync_mode=nobarrier and the optional SQLCipher 5 migration should also be noted. ## Not confirmed
- [corrected] (claim 3) Issues #81 and #89 show that SQLCipher's seam with Room produced AbstractMethodError crashes in 2026.
  - evidence: Both issues are real and both are CLOSED (stateReason COMPLETED). #81 (2026-01-20): the reporter wrote on 2026-04-08: 'The crash is happening when minSdk is set to 23. No crash when it's 24'. It was fixed by an explicit override in 4.15.0. #89 (2026-07-10) reports: 'Result with minSdk 24 ... no crash' and 'the exposure is limited to builds where the desugaring classpath is incomplete'. javap shows SQLiteDatabase has 1 of the 2 read-only-transaction overrides in 4.17.0 and both in 4.18.0.
  - correction: Both AbstractMethodError reports are fixed: #81 in 4.15.0 and #89 by 4.18.0. Both reproduced only with minSdk 23 together with incomplete default-method desugaring. Neither would affect this app at minSdk 24.
- [corrected] (claim 3) Issue #85 describes connection-pool hook problems.
  - evidence: #85 is CLOSED. The maintainer, sjlombardo, wrote: 'The postKey method uses PRAGMA cipher_default_page_size which is causing an inconsistent state when connection pooling is enabled', and advised moving it to preKey or using the per-connection cipher_page_size. The reporter then closed it: 'it appears to be due to a misconfiguration on my end rather than a bug in your library.'
  - correction: #85 is a closed report of user misconfiguration, not a library bug. It does show a real pitfall: global cipher_default_* PRAGMAs in postKey break pooled WAL connections. That supports the report's 'subtle' rating, not a defect count.
- [corrected] (claim 5) Google Play blocks updates without 16 KB support from 2027-02-01 for apps targeting API 35 or higher.
  - evidence: developer.android.com/guide/practices/page-sizes (last updated 2026-09-16): 'all apps targeting Android 15 (API level 35) and higher must support 16 KB memory page sizes on 64-bit devices on Google Play. Starting February 1, 2027, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates.' The Play Console Help page 'Play Console technical quality requirements' (answer 17492799) lists under Current Requirements: 'new app bundles uploaded to Play Console must support them ... 16 KB memory page size support: Apps that contain native code must support devices with 16 KB memory page sizes. Java/Kotlin only apps are compatible by default.' It also gives Wear OS 'Required as of 15 Sep, 2026' and TV 'Required as of 1 Aug, 2026'. The Android Developers Blog (May 2025) says: 'Starting November 1st, 2025, all new apps and updates to existing apps submitted to Google Play and targeting Android 15+ devices must support 16 KB page sizes.' The same guide now requires a RELRO test as well as LOAD alignment: '(VirtAddr + MemSiz) % 0x4000 == 0'.
  - correction: The requirement already applies today. Since 2025-11-01, new apps and updates targeting API 35 or higher must support 16 KB pages on 64-bit devices, so this new app, targeting 37, must comply from its first upload if it ships any native code. 2027-02-01 is the date after which non-compliant updates cannot be released at all. Compliance as the guide defines it means 16 KB LOAD alignment plus a 16 KB-aligned GNU_RELRO end, plus zip alignment.
- [corrected] (claim 10) Not on the list but copied into the code sketch: Os.open, Os.fsync and Os.rename exist since API 21 and throw ErrnoException; java.nio.file.Files is unusable at minSdk 24.
  - evidence: Local api-versions.xml (android-37.0): android/system/Os since="21", and open, fsync, rename and close carry no later since. javap on android.jar shows 'public static java.io.FileDescriptor open(java.lang.String, int, int) throws android.system.ErrnoException' and the same throws clause on fsync, rename and close. java/nio/file/Files is since="26". DataStore FileMoves.android.kt:34 has @RequiresApi(26). However, developer.android.com/studio/write/java8-support says: 'With Android Gradle plugin 7.4.0 or higher, additional Java 11 APIs are supported such as a subset of the java.nio.file package' (desugar_jdk_libs_nio 2.1.5 is on Google Maven).
  - correction: The Os facts are confirmed. java.nio.file.Files is not on the platform before API 26, but core-library desugaring provides a subset of it. 'Unusable' overstates the case; Os.* is still the simpler, better-understood choice.

## Missed issues
- The 16 KB check is incomplete, so the advice on SQLCipher versions is wrong in a way that matters. Today's page-sizes guide (updated 2026-09-16) adds a RELRO test, '(VirtAddr + MemSiz) % 0x4000 == 0', and says a misaligned RELRO 'crashes the app at runtime with a segmentation fault'. I ran readelf -lW on all four ABIs of each AAR. sqlcipher-android 4.17.0, 4.18.0 and 4.19.0 fail the test: RELRO end mod 16K is 0x1000 or 0x2000 (4.19.0 arm64: 0x1faab0+0x6550). Only 4.19.1 passes (MemSiz 0x9550, end 0x204000). Its release notes say 'Add common-page-size linker flag', which matches Android.mk:68 '-Wl,-z,common-page-size=16384'. The report checked LOAD p_align only, a test the three failing versions also pass. If A is ever chosen, pin 4.19.1 or later and run the guide's RELRO test as well. This also bears on the app comparison: KeyGuard pins sqlcipherAndroid = "4.19.0" (gradle/libs.versions.toml:181 today), and the report says Passbolt uses 4.18.0. Whether a given library actually crashes depends on its layout. In the cases I examined the next writable segment starts on a new 16 KB page, so say 'fails Google's test', not 'crashes'.
- The report says B has no native code, which is not true for the app as designed. docs/research/crypto.md picks com.lambdapioneer.argon2kt:argon2kt:1.6.0, a native library, as the Argon2 implementation. I downloaded the 1.6.0 AAR from Maven Central. All of its LOAD segments are 0x4000-aligned. Under the guide's RELRO test, its arm64-v8a libraries pass, but armeabi-v7a (0x1000), x86 (0x2000) and x86_64 (0x2000) fail; for example, x86_64 libargon2jni.so has RELRO 0x36ab0+0x3550. Play's requirement covers 64-bit devices, which include x86_64. The app is new and targets 37, and new uploads have had to support 16 KB since 2025-11-01, so B's 16 KB exposure exists now, not in 2027.
- Pixel devices do not run the f2fs default the report cites. AOSP fstabs mount /data as f2fs with fsync_mode=nobarrier: device/google/coral fstab.hardware, device/google/gs201 conf/fstab.gs201.in:18, and device/google/zuma conf/f2fs/fstab.zuma.f2fs:7. Per f2fs.rst:273-275, '"nobarrier" is based on "posix", but doesn't issue flush command for non-atomic files'. So on Pixels a successful fsync does not flush the drive's volatile cache, and durability rests on the storage hardware. The write, fsync, rename, directory-fsync procedure is still right. But the report should not promise more durability than this, and the fact strengthens the case for never overwriting the previous generation and for keeping several.
- The report says A means 'later a format migration of the user's only copy' when SQLCipher 5 lands. Zetetic's 5.0.0-beta post contradicts this: you can 'Open older databases without migrating using PRAGMA cipher_compatibility', or set it process-wide with PRAGMA cipher_default_compatibility = 4. Migration is optional. That weakens one of the report's reasons against A, though the beta itself warns 'not in production'.
- Part of the case against A rests on issues that do not apply here. The section-4 claim that 'in 2026 alone A's seam with Room produced AbstractMethodError crashes (#81, #89)' omits that both are fixed (4.15.0 and 4.18.0) and both reproduced only at minSdk 23 with incomplete desugaring. This project's minSdk is 24. #85 was closed by its reporter as his own misconfiguration. Of the cited issues, only #91 (open, unanswered, roughly 3x slower first unlock) and #93 (fixed in 4.19.1, wrapper path only) remain. The recommendation for B still stands on the other grounds: the Room 3 transition, the 7-week-old driver and the sidecar file. But the user should not be told SQLCipher is crash-prone on that basis.
- The Room 2 maintenance statement is credited to the 'Room 3 release notes' as well as the blog. The release-notes pages contain no maintenance statement; only the 2026-03-13 blog makes the promise. Also, Room 2.8.5 shipped on 2026-09-09, after Room 3 went stable on 2026-07-01, so patches have already continued past the promised end date.
- The report lists KeePassJava2 3.1.0 as a 'Latest stable' option without saying how new it is. It is one day old and the fourth release in four days (GitHub releases: 2.2.5 on 2026-10-02, 2.2.6 and 3.0.0 on 2026-10-03, 3.1.0 on 2026-10-05), after a 19-month gap since 2.2.4 (2025-03-05). The 3.x line also renames its artifacts (KeePassJava2.kdbx.database, KeePassJava2.kdbx.io) and compiles for Java 17. It should not be presented as a settled dependency.
- The KeePassDX zero-byte evidence fits export more than internal storage. Two of the three cases (#1594 Dropbox, #1620 DAVx5/WebDAV) were writes through third-party document providers that reported success while leaving 0 bytes; the maintainer says the provider never raised an exception. That most directly supports the report's export rule: re-read and checksum the copy written through the system file picker before reporting success. That rule should be treated as mandatory and not trimmed later, because a provider's 'no exception' is not proof the write succeeded.
