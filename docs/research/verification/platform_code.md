# Verification: platform (code lens) — independent check, 2026-10-06

## Overall
Within the code-and-artifact lens the report is mostly reliable. All 16 API levels match api-versions.xml and android.jar. The Compose autofill, saveable-state and RevealLastTyped defaults, the androidx.core 1.18 FingerprintManagerCompat no-op, the ClipboardService rules and most reference-app file citations match the bytecode and the AOSP android17 source. Before relying on it, fix five things. First, the biometric API matrix: on API 29 a Class-3 check returns UNKNOWN, Android 9 fails only on Samsung with a CryptoObject, and 24-27 errors are immediate, not silent. Second, the ProcessLifecycleOwner timing: the 700 ms counts from the last pause, and SAF screens trigger a lock. Third, the Proton root-detection and taskAffinity statements. Fourth, clearText() leaves the password in undo history. Fifth, decor-level filterTouchesWhenObscured and importantForAutofill do not protect Compose nodes the way they protect Views.

## Not confirmed
- [corrected] (claim 4) Which API levels take the FingerprintManagerCompat path in 1.1.0: report expects 'no hardware' on API 24-27, 'unknown' on 28; behaviour on 29+.
  - evidence: VP/x/BM110.javap.txt:36-271 (BiometricManager 1.1.0): the constructor obtains FingerprintManagerCompat only for SDK <= 29. canAuthenticateCompat has branches for SDK == 29, SDK == 28 and below 28. BiometricFragment.isUsingFingerprintDialog (BF110.javap.txt:1111-1160) is true for SDK < 28, and on 28 when a CryptoObject is used and DeviceUtils.shouldUseFingerprintForCrypto applies (vendor list res crypto_fingerprint_fallback_vendors = 'samsung'), or when FEATURE_FINGERPRINT is missing. checkForFingerprintPreAuthenticationErrors returns 12. AOSP android10-release BiometricManager.java has only canAuthenticate(), not canAuthenticate(CryptoObject), so the reflective call in Api29Impl.getCanAuthenticateWithCryptoMethod returns null. assume_strong_biometrics_models = Pixel 4 and Pixel 4 XL, and applies below 30 only. 1.2.0-alpha05 has the same gates and lists.
  - correction: With androidx.core 1.18 or later: (1) API 24-27: canAuthenticate(BIOMETRIC_STRONG or WEAK) returns BIOMETRIC_ERROR_NO_HARDWARE (12). authenticate() immediately calls onAuthenticationError(ERROR_HW_NOT_PRESENT = 12); it does not hang. If DEVICE_CREDENTIAL is allowed, canAuthenticate returns SUCCESS on a secured device and authenticate goes straight to the KeyguardManager credential screen. (2) API 28: canAuthenticate returns BIOMETRIC_STATUS_UNKNOWN (-1) only when FEATURE_FINGERPRINT is declared and a secure lock is set, otherwise NO_HARDWARE (12). authenticate() uses the framework BiometricPrompt and works, except with a CryptoObject on Build.MANUFACTURER 'samsung' or without FEATURE_FINGERPRINT; those cases take the stubbed dialog and get ERROR_HW_NOT_PRESENT. (3) API 29: authenticate() always uses the framework prompt and works. canAuthenticate(BIOMETRIC_WEAK) gives the framework answer. canAuthenticate(BIOMETRIC_STRONG) returns BIOMETRIC_STATUS_UNKNOWN on every device with an enrolled biometric except Pixel 4 and 4 XL; with core 1.17 it returned SUCCESS for fingerprint devices. (4) API 30 and later: framework calls only, unaffected. So a 'Class 3 only, require BIOMETRIC_SUCCESS' gate works only from API 30, not 29.
- [corrected] (claim 5) Reads need focus or being the default input method.
  - evidence: ClipboardService.java android17 1383-1428: reads are also allowed for READ_CLIPBOARD_IN_BACKGROUND holders (signature|role, framework manifest line 9057), the default IME (1388-1389), the focused UID (1400-1402), the system Content Capture service (1404-1412), the Augmented Autofill service (1413-1421) and virtual-device owners (1422-1427). getPrimaryClip also returns null while the device is locked (688). AOSP pie-release ClipboardService.clipboardAccessAllowed (line 622) says 'Installed apps can access the clipboard at any time'. The focus check (isUidFocused) first appears in android10-release (line 769).
  - correction: From Android 10, background reads are denied unless the caller is the focused app, the default IME, the system Content Capture or Augmented Autofill service, a READ_CLIPBOARD_IN_BACKGROUND holder or a virtual-device owner. On API 24-28 any installed app can read the clipboard at any time.
- [corrected] (claim 10) Bitwarden sets FLAG_SECURE at MainActivity.kt:253.
  - evidence: MainActivity.kt:251-257 updateScreenCapture(isScreenCaptureAllowed): line 253 is window.clearFlags(FLAG_SECURE) and line 255 is window.addFlags(FLAG_SECURE).
  - correction: FLAG_SECURE is added at MainActivity.kt:255 (cleared at 253) inside updateScreenCapture, and the user's screen-capture setting toggles it.
- [corrected] (claim 10) Proton Pass has a launcher activity with taskAffinity=''.
  - evidence: app/src/main/AndroidManifest.xml:17 sets android:taskAffinity='' on the <application> element. The launcher .ui.MainActivity (132-145) is singleTop and declares no affinity of its own.
  - correction: Proton sets taskAffinity='' application-wide, so it applies to the singleTop launcher and to every other activity that does not override it.
- [corrected] (claim 10) None of the three apps has root detection.
  - evidence: The three repositories' own code has none. Proton Pass depends on me.proton.core:challenge 36.8.0 (app/build.gradle.kts:359, pass/data/impl/build.gradle.kts:72). Its ChallengeFrame$Device/$Username/$Recovery builders call me.proton.core.util.android.device.DeviceUtilsKt.isDeviceRooted(Context) and serialize a 'rooted' boolean. util-android-device-36.8.0 isDeviceRooted checks Build tags 'test-keys', /sbin/su, /system/xbin/su and 10 other su paths, '/system/xbin/which su', and packages such as eu.chainfire.supersu and com.koushikdutta.superuser (VP/proton). The Cure53 report BWN-11-003 (root detection) is marked 'Status: Accepted' for Bitwarden.
  - correction: Bitwarden and KeePassDX have no root detection. Proton Pass ships root detection through its Proton Core dependency, which reports a 'rooted' flag in its anti-abuse challenge frames; it does not block or warn the user.
- [corrected] (claim 11) ProcessLifecycleOwner delivers ON_STOP 700 ms after the last activity stops (lifecycle-process 2.11.0).
  - evidence: lifecycle-process-2.11.0.aar (sha1 verified) ProcessLifecycleOwner: TIMEOUT_MS = 700L. activityPaused() decrements resumedCounter and, at 0, calls handler.postDelayed(delayedPauseRunnable, 700). The runnable dispatches ON_PAUSE and then dispatchStopIfNeeded(). activityStopped() calls dispatchStopIfNeeded(), which sends ON_STOP only when startedCounter == 0 and pauseSent is set. attach() registers Application ActivityLifecycleCallbacks, so only this app's activities count.
  - correction: The 700 ms timer starts when the last resumed activity pauses, not when it stops. ON_STOP arrives at the later of the last activity's onStop and pause + 700 ms. It usually lags onStop by under 700 ms and can arrive together with onStop.

## Missed issues
- TextFieldState.clearText() does not wipe the password, although section 3.3 lists it under key wiping. In foundation 1.12.1, clearText() is edit { delete(0, length) } (sources TextFieldState.kt:778-783). commitEdit records every programmatic change in undo history ('programmatic edits contribute to undo history without merging', TextFieldState.kt:266-273). Typed edits are recorded too, and no secure-field code path uses ClearHistory. So the cleared master password stays in TextUndoManager, and with rememberTextFieldState it is also written to saved state through TextUndoManager.Saver. Removing it needs state.undoState.clearHistory(), but undoState is @ExperimentalFoundationApi (TextFieldState.kt:228). The alternative is to drop the TextFieldState object.
- Section 3.5 says accessibility data sensitivity is 'implied by filterTouchesWhenObscured'. That holds for Views but not for Compose content. AccessibilityRecord.setSource copies the host view's sensitivity (AOSP android17 AccessibilityRecord.java:158-168). ui 1.12.1 then overwrites it with the node's own isSensitiveData, which is false unless set (AndroidComposeViewAccessibilityDelegateCompat.android.kt:1350-1360). createNodeInfo hides only nodes whose own config has IsSensitiveData = true (:536-541). AccessibilityInteractionController.findAccessibilityNodeInfoByAccessibilityIdUiThread checks only isShown() on the host (AccessibilityInteractionController.java:372-374). Result: with only the decor flag, non-tool accessibility services still receive events and node info for Compose nodes. isSensitiveData is per node and not inherited, so it must be set on each secret node to get this protection, and it does nothing below API 34.
- The decor-view autofill opt-out (the section 3.6 'Window opt-out' row) cannot be relied on from Android 14. The AOSP Javadoc (View.java:10642-10648 and 10713-10721) says the contents of NO_EXCLUDE_DESCENDANTS views are still included in the ViewStructure. ViewGroup.populateChildrenForAutofill (ViewGroup.java:3862-3871) adds children through device-config heuristics regardless of importance. Android 17 AutofillFeatureFlags turn trigger_fill_request_on_unimportant_view and include_all_autofill_type_not_none_views_in_assist_structure on by default (AutofillFeatureFlags.java:404-412). Compose's virtual AutofillManager.notifyViewEntered(View,int,Rect) is not gated by the host view's importance (AutofillManager.java ~2020-2043). Treat the per-field ContentDataType.None as the main control and test on API 26-33 and 34+.
- ContentDataType.None leaves some autofill traffic in ui 1.12.1. PopulateViewStructure still writes the field's EditableText as the node's autofill value (PopulateViewStructure.android.kt:136-141). It still adds the node, because isRelatedToAutofill counts the ContentDataType key (AndroidAutofillManager.android.kt:365-373). A ContentType.Password hint, which KeyboardType.Password and BasicSecureTextField set automatically, keeps the node 'related to auto-commit' (:361-363, 289-299, 339-349). Compose then still sends visibility notifications and calls AutofillManager.commit(). Read-only and disabled text fields are autofill nodes with their text too (claim 1), so stored passwords should be shown with Text, not with read-only TextFields.
- Biometrics: 'stable 1.1.0 with biometrics effectively API 29+' does not follow from the bytecode under the report's own 'Class 3 only' rule. On API 29, canAuthenticate(BIOMETRIC_STRONG) returns BIOMETRIC_STATUS_UNKNOWN on everything except Pixel 4 and 4 XL (claim 4). Errors on 24-27 are immediate ERROR_HW_NOT_PRESENT, not silent hangs. Android 9 fails only on Samsung with a CryptoObject. core 1.18 or later cannot be avoided by pinning: the activity-1.13.0 and activity-compose-1.13.0 POMs depend on androidx.core:core-ktx 1.18.0, and 1.13.0 is the latest stable activity, so every current Compose app gets the no-op FingerprintManagerCompat. Bitwarden itself ships biometric 1.2.0-alpha05 with core 1.19.0 and minSdk 29 (gradle/libs.versions.toml:11,18,22).
- biometric 1.4.0-alpha07 merges androidx.biometric.internal.ui.FingerprintDialogActivity (exported=false, Theme.AppCompat.Dialog.Alert) into the app manifest. Its Context-based handler, AuthenticationHandlerFingerprintManager, starts that activity with Intent.FLAG_ACTIVITY_NEW_TASK through Context.startActivity (bytecode: addFlags(268435456)). With the report's taskAffinity='' launcher, on API 23-27 this window can open in a separate task, without our FLAG_SECURE or filterTouchesWhenObscured, and stop our activity. The classic BiometricPrompt(FragmentActivity, ...) constructor uses the in-activity FingerprintDialogFragment instead. This needs an API 24-27 test before choosing the 1.4 API surface.
- ProcessLifecycleOwner counts only this app's activities (lifecycle-process 2.11.0 attach() registers Application.registerActivityLifecycleCallbacks). The SAF picker (DocumentsUI), the share sheet and KeyguardManager's confirm-credential screen therefore make it emit ON_PAUSE and ON_STOP about 700 ms after our activity pauses. A lock-on-ON_STOP design will lock in the middle of the encrypted export and import that section 1 makes mandatory, unless it adds a grace window for activities it launches itself.
- Clipboard on old devices: the 'background app cannot check the clipboard' surprise holds only from Android 10. In pie-release, ClipboardService says 'Installed apps can access the clipboard at any time' (line 622 onward), and auto-clear exists only from android13-release. On API 24-28 (inside our minSdk 24) any background app can read a copied password, and on API 24-32 the app's own timed clear is the only clearing. Proton shows a fail-closed alternative to KeePassDX's compare-then-clear: when the background read fails (hasPrimaryClip() is false, giving CouldNotGetClipboardContent), it clears anyway (ClearClipboardBroadcastReceiver.kt onReceive; ClipboardManagerImpl.kt:101-114).
- WorkManager 2.12.0 also merges two exported components: SystemJobService, protected by BIND_JOB_SERVICE, and DiagnosticsReceiver, protected by DUMP. It also adds a disabled BOOT_COMPLETED receiver and pulls in room-runtime 2.7.0 (work-runtime-2.12.0.pom). profileinstaller 1.4.1 adds a DUMP-protected exported receiver. The 'one exported activity' rule still holds, but the merged-manifest review should expect these components.
- Many '[androidx source]' files in the author's scratchpad (AUTH/androidx) are androidx-main, not the shipped versions. SecureTextField.kt there defaults textObfuscationMode to System (lines 143 and 311), while material3 1.4.0 (sources jar and bytecode) uses RevealLastTyped. AndroidDialog.android.kt, SemanticsProperties.kt, AndroidComposeView.android.kt, KeyboardOptions.kt and TextFieldState.kt also differ substantially from the 1.12.1 -sources.jars. AndroidAutofillManager.android.kt and PopulateViewStructure.android.kt are byte-identical to 1.12.1. Every source-tagged claim should be re-checked against the versioned sources jar (VP/src/ui-1.12.1, foundation-1.12.1, material3-1.4.0).
- Minor: the header says Bitwarden 2026.9.1 at HEAD, but the HEAD tree's appVersionName is 2026.9.0 (gradle/libs.versions.toml:6); 2026.9.1 is the latest release tag. Proton's Settings.Global.BOOT_COUNT read is in pass/biometry/impl/.../BootCountRetriever.kt:37, which NeedsAuthChecker consumes. Other spot-checked citations are accurate: VaultLockManagerImpl.kt:753, K/timeout/ClipboardHelper.kt:82-87, backup_rules.xml:21, Bitwarden's launchModeAPIlevel (singleTask below 30), intentMatchingFlags (attr since 36) and the three Bitwarden lockfiles.
