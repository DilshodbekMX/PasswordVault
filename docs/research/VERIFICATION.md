# Verification of the research: corrections that change the build

On 2026-10-06 ten independent checkers re-tested the five research reports against primary sources: source code at the cited lines, the published artifacts (AARs, jars, `android.jar`), AOSP `android17-release`, Maven metadata, and official documentation, standards and audit reports. Each report had one checker for code and artifact claims and one for documentation and published facts. Their full findings, with file and line evidence, are in [verification/](verification/).

## Results

| Report | Confirmed | Corrected | Refuted | Unverifiable |
|---|---|---|---|---|
| account-based.md | 83 | 11 | 0 | 1 |
| offline.md | 74 | 8 | 1 | 0 |
| crypto.md | 76 | 16 | 0 | 0 |
| storage.md | 63 | 11 | 2 | 0 |
| platform.md | 86 | 15 | 0 | 0 |

No recommendation was overturned. The local-only design, Argon2id with a wrapped random vault key, AES-256-GCM, one sealed file written as new generations, and biometric unlock through a Keystore key and `CryptoObject` all stand. The corrections are in the details below, and several of them are the difference between a vault that can lose data and one that cannot.

Where this file and a research report disagree, this file wins. Each item has an ID so that the design documents can cite it.

## Cryptography (crypto.md)

| ID | Correction | What to build |
|---|---|---|
| V-C1 | argon2kt 1.6.0 hashes the whole *capacity* of the password and salt buffers, not their position or limit (`Argon2Jni.cpp:33-39`). Its raw-hash output is `malloc`ed native memory that is never zeroed or freed. `rawHashAsByteArray()` and `encodedOutputAsString()` make extra heap copies. | Allocate direct buffers of exactly the input size and pass the same bytes to both Argon2 implementations. Copy the key out once and overwrite the returned buffers. Never call the two convenience methods and never store the encoded string. |
| V-C2 | Loading argon2kt can fail on some devices (issue #25: Transsion/Unisoc, Huawei), and the failure is `UnsatisfiedLinkError`, an `Error`. The Bouncy Castle fallback needs about 80 MB of Java heap for 64 MiB (OOM at `-Xmx76m`, fine at `-Xmx80m`), while the CDD guarantees only 48 MB (hdpi) or 80 MB (xhdpi) without `largeHeap`. | Catch `Throwable` around the native load. Set `android:largeHeap="true"`. Before running the fallback, check `Runtime.maxMemory()` minus used memory and show a clear "this phone does not have enough memory" error instead of crashing. |
| V-C3 | The body's associated data was defined two different ways (with and without the body nonce). | AAD = magic ‖ header_len ‖ header bytes exactly as stored, excluding the body nonce. Ship a whole-file test vector. |
| V-C4 | The reader rules accepted a file with no password slot, did not pin `argon2_version`, and left duplicate keys, unknown keys, trailing data and file size open. | Require exactly one password slot. Require `argon2_version == 19`. Reject duplicate keys, unknown keys and trailing bytes. Cap the file size. In version 1, require the exact KDF constants rather than a range: Conscrypt buffers the whole ciphertext and 256 MiB of Argon2 cannot run on the fallback. |
| V-C5 | **The change-password flow could lose the vault.** The new password was typed once, the read-back reused in-memory bytes, and the biometric key and older generations were deleted before the new file was proven. One typo meant no way back in. | Type the new password twice. Prove the new file by reading it from disk and unlocking it with the re-typed password through the normal unlock path. Delete the old Keystore key only after the new file is committed. Keep the previous generation until the first successful unlock with the new password. Re-enrol biometrics while the vault is still unlocked. Use "type twice" for creation and for backup passwords too. |
| V-C6 | `KeyStore.containsAlias()` returns false on *any* Keystore error, not only when the key is gone, and every other Keystore error surfaces as a plain `InvalidKeyException` (`AndroidKeyStoreSpi.java:158-179`, `KeyStoreCryptoOperationUtils.java:117-127`). Aegis's "plain `InvalidKeyException` means invalidated" heuristic is wrong. | Remove a biometric (or other device) slot only on `KeyPermanentlyInvalidatedException` from `Cipher.init`, or when `getKey()` returns null. Treat `containsAlias() == false` and a plain `InvalidKeyException` as temporary: hide the option for this session and change nothing. |
| V-C7 | Keys with user authentication: the default is *no* authentication. Only after `setUserAuthenticationRequired(true)` do the defaults become per-use and `AUTH_BIOMETRIC_STRONG`. The biometric wrap's IV must come from `cipher.iv`, because Keystore rejects a caller IV with randomized encryption. | Call `setUserAuthenticationRequired(true)`, `setKeySize(256)` and `setInvalidatedByBiometricEnrollment(true)` explicitly. Initialise for encryption without an IV and store `cipher.iv`. |
| V-C8 | Older files and backups remain openable after a password change; the design had no rollback signal. | Put a monotonically increasing generation number in the authenticated header, remember the highest seen, and warn on rollback. |
| V-C9 | NIST names the *stabilized-string* NFC process (UAX #15 §12.1): NFC plus rejecting unassigned code points. Plain `Normalizer.normalize(NFC)` does only half. NIST's 15-character rule is for centrally verified passwords; a local vault password is an analogy, not a binding rule. | At creation, reject code points whose `Character.getType` is `UNASSIGNED`; at every use, encode NFC then UTF-8. Add non-ASCII and NFC-versus-NFD test vectors. |
| V-C10 | `SecretKeySpec.destroy()` throws `AbstractMethodError` on API 24-25 (no default method before API 26). Conscrypt `Cipher` objects keep their own key copies. | Never call `destroy()`. Zero our own byte arrays and drop `Cipher` references promptly. |
| V-C11 | `TextFieldState.clearText()` records the deleted password in the undo history (capacity 100), and the keyboard undo shortcut restores it. `rememberTextFieldState` also saves that history. | Hold secret field state with `remember { TextFieldState() }`, never `rememberTextFieldState`. After reading it, call `clearText()` and `undoState.clearHistory()` (experimental API), or discard the state object. |
| V-C12 | `java.util.Base64` is API 26+. | Use `kotlin.io.encoding.Base64` or `android.util.Base64`. |
| V-C13 | The EFF long word list is CC BY 4.0: attribution, a licence link and a note of changes (filtering the four hyphenated words is a change) are required. EFF recommends six words; five is our own judgement (64.6 bits against 1,703 Argon2id guesses per second on an RTX 4090 at 64 MiB, t=3; parallelism does not slow the attacker). | Credit EFF on an About or licences screen. Tell the user that EFF recommends six words. |
| V-C14 | Bitwarden's `InsufficientKdfParameters` is a lower bound only, and KeePassDX's 3/4-of-memory check does not run when a file is opened (fixed separately in 4.5.0 as #2640). The recommendation to bound KDF cost before running it stands; only age's specification and KeePassDX #2640 support it. | Validate every KDF parameter from a file (ours or an imported one) against fixed bounds and device memory before deriving anything. |

## Storage (storage.md)

| ID | Correction | What to build |
|---|---|---|
| V-S1 | **`rename(2)` silently replaces an existing target.** "The target never exists beforehand" was an unenforced assumption; after a fall-back open, `loaded generation + 1` can overwrite a newer or a damaged file. | Allocate the next generation as 1 + the highest number among *all* names on disk, including temporary, damaged and quarantined files. Check that the target does not exist under the vault mutex and refuse otherwise. |
| V-S2 | A failed directory fsync was treated as "committed". | A save whose directory fsync fails is not reported as saved and triggers no pruning. Show a storage error; prune only after a later save's directory fsync succeeds. |
| V-S3 | **Refuted: the unkeyed SHA-256 trailer plus AEAD tags do not separate "damaged" from "wrong password" in every case** (bad bytes written before sealing, generations sealed under different passwords, damage confined to the trailer, header fields read before the check). | Report "wrong password" only when no retained generation's password slot opens with the typed password. A verified AEAD takes precedence over any checksum. Never offer a destructive "reset vault" in response to a wrong password. |
| V-S4 | **Refuted: "5 newest plus one per day for 14 days" can delete every good copy** (simulated: a new install with early bad saves, a clock jump, a bug persisting for 15 days). It also counted and later pruned damaged files. | Retention must know which generations are proven good and must not depend on the wall clock. Never prune below the newest N generations that were opened successfully from disk at a later app start. Move failed files to a quarantine name that pruning never touches. Pin the last generation of each app version. |
| V-S5 | After a password change, every retained older generation still opens with the old password. | Rotate the vault key on password change (as V-C5 requires). Keep old-password generations only until the new password has been proven by a successful unlock from disk, then retire them. |
| V-S6 | Export should copy what was verified, and document providers can report success after writing 0 bytes (KeePassDX #1594, #1620). | Export from the generation opened and verified in this session. After writing through the Storage Access Framework, read the file back and verify it before saying "done". This step is mandatory. |
| V-S7 | DataStore 1.2.1 is not atomic on API 26+ (`Files.move` without `ATOMIC_MOVE` is unlink-then-rename). `androidx.core.util.AtomicFile` swallows fsync and rename failures. | Do not use DataStore or `AtomicFile` for anything that must survive a crash. Use `Os.rename` (API 21) and never `Files.move` without `ATOMIC_MOVE`. |
| V-S8 | Pixels mount `/data` as f2fs with `fsync_mode=nobarrier`: a successful fsync does not flush the drive's cache. | Durability rests partly on hardware; keeping several proven generations is the defence. |
| V-S9 | 16 KB pages: Google Play has required 16 KB support for new apps and updates targeting API 35+ since 2025-11-01 (on 64-bit devices), and the guide now adds a RELRO test. argon2kt 1.6.0's arm64-v8a libraries pass; its armeabi-v7a, x86 and x86_64 libraries fail the RELRO test. | Ship release builds with `abiFilters` arm64-v8a and armeabi-v7a (32-bit is not subject to the rule). Keep x86_64 in debug builds for the emulator. |

## Android platform (platform.md)

| ID | Correction | What to build |
|---|---|---|
| V-P1 | **Fingerprint with androidx.biometric 1.1.0 or 1.2.0-alpha05, now that androidx.core ≥ 1.18 is unavoidable** (activity 1.13.0 depends on core 1.18.0, whose `FingerprintManagerCompat` is a no-op). API 24-27: `canAuthenticate` returns `BIOMETRIC_ERROR_NO_HARDWARE` and `authenticate` fails immediately. API 28: works, except with a `CryptoObject` on Samsung or without `FEATURE_FINGERPRINT`. API 29: `authenticate` works but `canAuthenticate(BIOMETRIC_STRONG)` returns `BIOMETRIC_STATUS_UNKNOWN` (except on Pixel 4). API 30+: unaffected. biometric 1.4.0-alpha05 and later carry their own fingerprint code, but their context-based API launches a separate `FingerprintDialogActivity` with `FLAG_ACTIVITY_NEW_TASK`, which may open outside our task without `FLAG_SECURE`; the classic `BiometricPrompt(FragmentActivity, …)` constructor uses an in-activity dialog. | Decide the library from the Android 7 and 9 emulator lab. In any case treat `STATUS_UNKNOWN` on API 29 as "offer it and let authentication decide", and if the 1.4 alpha is used, use only the classic constructor. |
| V-P2 | Clipboard by Android version: on API 24-28 any installed app can read the clipboard at any time; the system's one-hour auto-clear exists only on Android 13+ and restarts on every read; `clearPrimaryClip()` is API 28+ (set an empty clip below); from Android 10 a background app can neither read the clipboard nor learn that it changed, so an unconditional timed clear will also erase whatever the user copied later. Listener-based exact alarms need no permission but are dropped once the app is cached; inexact alarms have no one-hour bound under Doze or battery saver; WorkManager merges `WAKE_LOCK`, `ACCESS_NETWORK_STATE`, `RECEIVE_BOOT_COMPLETED`, `FOREGROUND_SERVICE` and exported components. | Choose the clearing mechanism from the clipboard lab's measurements. On API 24-28, compare before clearing (reading works there). Tell the user that a later copy may be cleared too, and that pinned items in a keyboard's clipboard history (Gboard) survive every clear, so they should never pin a password. |
| V-P3 | `ProcessLifecycleOwner` emits `ON_STOP` when the system file picker, the share sheet or the confirm-credential screen opens, so "lock on stop" would lock in the middle of export and import. Its 700 ms delay counts from the last pause. | Give activities the app launches itself (file picker, share) a grace window instead of locking. |
| V-P4 | Autofill: the decor-view `importantForAutofill = NO_EXCLUDE_DESCENDANTS` opt-out cannot be relied on from Android 14 (heuristics include unimportant views; Android 17 turns them on by default). Even with per-field `ContentDataType.None`, Compose still writes the field's text as the node's autofill value, and a password hint keeps auto-commit. Read-only and disabled text fields are autofill nodes containing their text. | Use per-field `ContentDataType.None` as the main control, verified by the window lab's logging autofill service. Display stored passwords with `Text`, never with a read-only `TextField`. |
| V-P5 | Accessibility: a decor-view `filterTouchesWhenObscured` does not make Compose nodes accessibility-sensitive; `isSensitiveData` is per node and not inherited, and works only on API 34+. | Set `semantics { isSensitiveData = true }` on every node that shows a secret. |
| V-P6 | **Backup and transfer:** at target 31+ device-to-device transfer ignores both `allowBackup` and `fullBackupContent` on every AOSP-based device, not just "some manufacturers". A missing `<cloud-backup>` section falls back to `fullBackupContent`; a missing `<device-transfer>` section transfers everything except no-backup and cache directories. A third, opt-in `<cross-platform-transfer>` section exists from Android 16 QPR2. On Android 7-11, `allowBackup="false"` blocks transfer entirely. | Write both `<cloud-backup>` and `<device-transfer>` explicitly, and state `allowBackup` explicitly. Keep every device-bound file (Keystore-wrapped blobs, PIN state) in `noBackupFilesDir`. If the vault file is allowed to transfer, a failed device-slot unwrap on the new phone must mean "PIN and fingerprint are off here", never "delete". |
| V-P7 | The predictive-back opt-out still exists at target 37; only edge-to-edge and large-screen orientation are enforced. Android 17's memory limiter and its "keyboard not restored after rotation" change apply to *all* apps. | Use `BackHandler` anyway. Test the KDF under `adb shell am memory-limiter manual <pid> <MB>`. Re-request the keyboard after rotation where needed. |
| V-P8 | Out-of-scope list additions: StrandHogg 2 on unpatched Android 7-10 (only the OS patch helps) and TapTrap (fixed only on Android 13-16). | Name them in the threat model's "we do not defend against" list. |
| V-P9 | Proton Pass sets `FLAG_SECURE` only on some activities; Bitwarden treats a missing timeout as "never". | Apply `FLAG_SECURE` to every activity that shows vault data. Store an explicit timeout default and treat a missing value as the strictest setting. |
| V-P10 | API levels for minSdk 24: `setInvalidatedByBiometricEnrollment` 24; `setIsStrongBoxBacked` and `setUnlockedDeviceRequired` 28; `setUserAuthenticationParameters` and `AUTH_BIOMETRIC_STRONG` 30 (below that, `setUserAuthenticationValidityDurationSeconds(-1)`); `ClipDescription.setExtras` 24 (with compileSdk 37 the `EXTRA_IS_SENSITIVE` constant is inlined and works at every level); `setRecentsScreenshotEnabled` 33. A Keystore AES key without `setKeySize` is 128-bit. | Gate each call by API level; set 256 bits explicitly. |

## Facts about other apps (what we tell the user)

| ID | Correction |
|---|---|
| V-A1 | Keepass2Android's main app has been missing from Google Play since about 2026-10-03; only "Keepass2Android Offline" is listed there, at the older 1.14-r0 (2025-09-20). Current versions come from GitHub. |
| V-A2 | KeePassDX states it "does not and will not offer" plaintext (CSV) import, so moving passwords from Google into it needs a computer. Since 4.3.0 it asks for user verification before showing or copying any protected field, unless the database is opened in a mode without it. Choosing Argon2 there keeps 16 MiB of memory and benchmarks the iterations to about one second. |
| V-A3 | Proton Pass: three wrong PINs at the lock screen fall back to the account password; they do not sign the user out (sign-out follows three wrong account passwords). It marks only secret fields as sensitive when copying. Its own pages claim offline access; this was not tested. |
| V-A4 | Bitwarden: of nine third-party reports for 2025, only one (Unit 42) covers the mobile apps. For V2 accounts the shipped SDK already seals each item as one AES-256-GCM blob; field-by-field encryption without associated data remains for V1 accounts (all Android registrations while a feature flag is off) and organisation items. ETH Zurich's "Issue 6" is a Medium icon-URL leak; field swapping is the paper's attack BW05. Self-hosting needs HTTPS but not a public domain or Docker specifically. |
| V-A5 | 2FAS Pass (BUSL-1.1, source-available, not open source) needs no account and is free for up to 200 items: the closest existing match to "no account". Keyguard's paid limits apply only to its Google Play build; its GitHub and F-Droid builds are unlocked. |
| V-A6 | Google says on-device encryption for Google Password Manager "will be set up for everyone" and cannot be removed; losing every recovery option then loses every password. Google's own help pages label the Android export step differently ("Export passwords & passkeys" or "Export passwords"). Chrome's CSV `name` column is a Chrome-derived site name, and one saved login can appear on several rows (one per affiliated domain). |
| V-A7 | Android now has a Credential Transfer API (`androidx.credentials:providerevents` 1.0.0-beta01, Android 8+) built on the FIDO Credential Exchange Format; KeePassDX calls it a must-have. Candidate for a later version, not version 1. |
| V-A8 | Padloc's last release, v4.3.0, was published on 2023-03-06 (the Atom feed's 2023-04-28 is an edit date); its Play app was last updated 2022-09-09. |
